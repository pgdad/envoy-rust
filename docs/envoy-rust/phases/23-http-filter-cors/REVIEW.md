## Named focus-item verdicts (all PASS)

The fix `typed_per_filter_config: r.typed_per_filter_config.clone()` (`hcm.rs:239`) is correct (`PerFilterConfig`/`CorsPolicy` derive `Clone`). Reviewer-grepped: this is the **only** production `Route`-from-`Route` hand-clone — all other production constructions populate the field directly from parsed config; the remaining `Route { typed_per_filter_config: … }` sites (H2 `hcm.rs:3575/3697`) are test code. `clone_route_config_preserves_typed_per_filter_config` (`hcm.rs:~1297` in diff) seeds a CORS policy, clones, and asserts the key survives — a genuine regression test for exactly this defect. The §6.2 "CRITICAL topology finding" of the implementation arc.
2. **The `resolve_route` / `build_response` mirror invariant (regression-equivalence) — PASS.** `resolve_route` (`crates/envoy-http1/src/hcm.rs:1200-1219`) is a textual structural mirror of `build_response`'s internal match (`:1208-1259`): both do `find_header(&req.headers, headers::HOST).filter(!is_empty)` → `strip_port` → `virtual_hosts.iter().find(vh_matches)` → `routes.iter().find(route_matches)`, calling the SAME free functions (`strip_port` :1275, `vh_matches` :1282, `route_matches` :1292). There is no input under which the up-front resolution and `build_response`'s independent re-match select different routes; `build_response` is left BYTE-IDENTICAL. The 30-fixture regression-equivalence claim is structurally supported, not merely asserted. Empty-host / no-vhost / no-route all yield `None` → `apply_route_config(None)` → CORS inert, while `build_response` independently produces its synth 400/404 (no per-route config exists on a non-matched route anyway) — no false coupling. Borrow soundness verified: `matched_route` borrows `config`; `apply_route_config` clones the policy into the instance, ending the borrow before the `mem::take` of the request fields (H1 `hcm.rs:614-621`, H2 `hcm.rs:456-465`). ### Minor (Nice to Have)

- **M23-1 (cluster A) — degenerate near-empty-`CorsConfig` test.** `cors_config_filter_chain_entry_is_near_empty` was correctly downgraded to `let _c = CorsConfig::default();` (a bare `@type`-tagged YAML can't deserialize into `CorsConfig` because `deny_unknown_fields` rejects the `@type` key — the tag is consumed by the outer `HttpFilterTypedConfig`, never reaching the inner struct), with an honest inline justification. The real coverage lives in `cors_filter_chain_entry_parses_to_cors_variant` (which parses the full `HttpFilter` YAML through the enum). The degenerate test is near-worthless rather than misleading; consider deleting it. No behavioral impact.
- **M23-2 (cluster A) — `resolve_route` not re-exported at the lib root.** It's `pub fn` in `pub mod hcm` and called fully-qualified as `envoy_http1::hcm::resolve_route` (H2 `hcm.rs:465`), which works but is slightly less tidy than the `build_response` precedent (which IS re-exported at `lib.rs:27`). Cosmetic: add `resolve_route` to the lib-root re-export for symmetry. No behavioral impact.
- **M23-3 (cluster A) — H2 threading test uses a `direct_response` route; add a clarifying comment.** `h2_cors_preflight_short_circuits_via_threading` asserts envoy-rust's preflight `StopAndSend` fires regardless of action type (the short-circuit happens on decode, before `build_response` inspects the action) — which is correct envoy-rust threading behavior and a valid unit-level proof, NOT a differential claim, so it does not contradict ADR-0058 L6 (an Envoy-vs-envoy-rust differential concern). A one-line comment to that effect would prevent future confusion. No behavioral impact.
- **M23-4 (cluster B) — backstop probe-3 comment mislabels L4 as the "L7 negative path."** `crates/envoy-bin/tests/http_filter_cors.rs:352-353` labels the disallowed-origin GET (L4 shared pass-through) as "L7 negative path — envoy-rust-only behavior." Probe 3 does not exercise L7 (the absent-filter fatal-reject); the file's own header note (`:14-22`) correctly states L7 is covered only by the unit test. Relabel to "L4 disallowed-origin pass-through" so a future reader doesn't believe the backstop covers L7. No behavioral impact.
- **M23-5 (cluster B) — no `ignore_case` / non-`Exact` origin-matcher coverage.** All tests and both fixture sides use `exact:` origins. The matcher is fully reused from `StringMatcher` (well-tested in `matcher.rs`, including `ignore_case` for prefix/suffix/contains), and CORS adds no matching logic of its own, so the risk is low. A prefix/`ignore_case` origin probe would be belt-and-suspenders. Not required.
- **M23-6 (cluster C) — `Connection: close` detection is whole-value-equality, not token-aware.** `hcm.rs:478-481` uses `v.eq_ignore_ascii_case("close")`, matching only a header whose entire value is exactly `close`. RFC 7230 §6.1 permits a comma-list (`Connection: keep-alive, close`); such a value would NOT trip the invalidate branch → a closing connection could still be re-pooled → the exact `UnexpectedEof`-502 this correction targets. Only Minor because (a) the differential `http1-echo-server` sends a bare `close` (fixture covered), and (b) the existing send-failure invalidate (`hcm.rs:502-503`) self-corrects after at most one spurious 502 — not a permanent stale-connection leak. Fix: split on `,` and check any trimmed token case-insensitively equals `close` (mirroring the `transfer-encoding` check at `client.rs:157-159`, which shares the same whole-value-equality shape).
- **M23-7 (cluster C) — HTTP/1.0 implicit-close / absent-`Connection`-header not treated single-use.** The correction only invalidates on an explicit `Connection: close`; an HTTP/1.0 upstream (or any response with no `Connection` header) is single-use by default per RFC 7230 §6.3 yet would be re-pooled. Only Minor because the H1 client/pool target HTTP/1.1 keep-alive upstreams, no fixture exercises a 1.0 backend, and the send-failure invalidate is again the backstop. Recommended: record the HTTP/1.1-keep-alive-upstream assumption in BEHAVIOR_CONTRACT next to the existing `Connection: close` single-use note.

**Confirmed-correct observations (NOT findings).** (a) The `PerFilterConfig` single-variant irrefutable-`let` is forward-fragile by design — adding a second variant turns every such binding into a non-exhaustive compile error, which is the DESIRABLE §6.3 "force revisiting consumers" property, not a defect. (b) The local `header_ci` duplication in `cors.rs:236-241` is the sanctioned SC2 decision (the shared-util extraction is the standing-deferred M18-9/M21-3 item — N≥8 backstops). (c) The L7 absent-filter negative path has no end-to-end runtime assertion (only the parse-level unit test), a deliberate documented cost/benefit call — the unit test does hit the exact `parse_bootstrap` path before any runtime starts. (d) Multiple-`origin` / empty-`origin`-value inputs are untested but behave identically on both proxies (H1 passes headers verbatim; the matcher treats the value like any string) — not a differential risk. (e) The pre-existing H1 client framing assumption (a response with neither `Content-Length` nor chunked is treated as length-0 rather than read-to-close, `client.rs:179-209`) is load-bearing for Correction 2's safety but orthogonal to and unchanged by this phase — flagged so it is not mistaken as covered. (f) H2 correctly needs no `Connection: close` analogue (it's an H2-forbidden hop-by-hop header stripped at `response.rs:38`; H2 uses GOAWAY for connection lifecycle, and `H2PoolGuard` is keyed on stream multiplexing).
