**M1. `TokenBucketState::try_acquire` CAS-shape race on the refill path.** `crates/envoy-filter/src/local_rate_limit.rs:215-287` — the CAS at line 263 reads `compare_exchange(current, next, ...)` where `current = self.tokens.load(...)` (pre-refill value) and `next = available - 1`. When `available = current + 1` (i.e., exactly one interval elapsed AND `tokens_per_fill = 1`), `next` collapses to `current`, making the CAS `compare_exchange(current, current)` — which succeeds unconditionally for any concurrent thread observing the same `current`. Two threads observing the same `current` value in this scenario both succeed their CAS, both return `true`, and the single refill token is "consumed" twice. **Why it matters:** real concurrent double-consumption bug on the refill path. **Why it does NOT rise above Minor at phase-09 scope:** the bug is exercised only when `tokens_per_fill > 0` AND a refill interval elapses concurrently with multiple acquires AND the refill credit per interval is exactly enough to bridge `current → current + 1`. Phase 09's actual exercise paths all avoid the contested arm: fixture 0016 uses `tokens_per_fill: 3` with `fill_interval: 60s` (the 5-probe burst completes in <1s; no refill triggers); the in-process backstop uses `tokens_per_fill: 2` with `fill_interval: 60s` (4-probe burst; same shape); the torture test uses `tokens_per_fill: 0` (no refill path exercised at all). The token cap at `max_tokens` provides a hard ceiling on over-crediting — even under adversarial concurrent refill, the bucket cannot exceed `max_tokens` so the blast radius is bounded. A secondary TOCTOU on the `last_fill_instant` overwrite (lines 266-278) compounds the bug but does not change its severity. **Fix sketch:** either (a) require `available > current` as a precondition for the CAS by structuring as `if available > current { self.tokens.store(available, ...); /* re-load + CAS down */ }`, OR (b) replace `compare_exchange(current, next)` with a token-decrement loop that re-loads on every iteration AND atomically combines the refill-credit with the consume by writing `available` then immediately CAS-ing down to `next = available - 1` (requires the second CAS to fail-and-retry if any other thread won). Option (b) is the closer match to the existing single-CAS shape; option (a) is structurally cleaner. ~15-30 LoC + an additional torture test exercising the contested path. **Disposition:** awareness-only forward-looking correctness note; **close at whichever future HTTP-filter-family phase first exercises non-zero `tokens_per_fill` within a refill-window-spanning burst**, OR at a dedicated token-bucket hardening pass.
