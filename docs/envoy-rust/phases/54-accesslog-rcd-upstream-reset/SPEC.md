## §1 — Why this pick

`%RESPONSE_CODE_DETAILS%` already renders in all three encoders and is set per response-path at the H1 record-build sites (phase 42, ADR-0099; failure paths `no_healthy_upstream` [45], `route_not_found` [46/47], `upstream_reset_before_response_started{overflow}` [50]). This phase is the **cheapest-strong-differential leaf available** and the natural completion of phase 53:

- **The trigger is already fully built — zero new harness.** Phase 53 (ADR-0110) built the accept-then-close upstream: the `tcp-echo-server --close-on-accept` helper mode (`tests/helpers/tcp-echo-server/src/main.rs`), the `TcpCloseBackend` harness struct (`tests/differential/src/backend.rs:92`), and the marker-driven launch arm (`tests/differential/src/lib.rs:3277` — `{{CLOSE_BACKEND_PORT}}` auto-spawns `TcpCloseBackend`). Fixture 0062 reuses ALL of it by including the same `{{CLOSE_BACKEND_PORT}}` / `{{BACKEND_HOST}}` markers — so this phase is even cheaper than phase 53 (which had to BUILD the backend) AND cheaper than the typical witness phase (no new fixture topology to design).
- **The rcd is set on a path that today emits the WRONG value.** envoy-rust's reset path emits the shared `via_upstream` rcd (`BEHAVIOR_CONTRACT.md:1020`), diverging from Envoy's `upstream_reset_before_response_started{connection_termination}`. No fixture witnesses the reset rcd today (fixture 0061 logs `{rc,rf}`-only). This phase sets the correct deterministic string and witnesses it byte-exact — the same shape as phase 50's `{overflow}` rcd correction/witness on the sibling overflow path.
- **State-0 recon-CONFIRMED + structurally PROVEN.** The recon (this session) emits `rcd:"upstream_reset_before_response_started{connection_termination}"` byte-stable across repeats AND a restart; and the `upstream_reset_before_response_started{<fixed-enum>}` family is already proven byte-exact deterministic by fixture 0058 (`{overflow}`, phase 50). So the determinism risk the LESSON warns about (brace/OS-text content) is DISPROVED for this specific reset-reason.
- **Completing phase 53 simplifies the code.** Phase 53 introduced the `reset_for_log` boolean ONLY because the reset rcd was indistinguishably `via_upstream` — so the `UC` flag could not key on the rcd (UNLIKE `UO`, which keys on `{overflow}`). Making the rcd unique lets `UC` derive 1:1 from the rcd (the `UO` precedent) and **removes** the boolean — a net simplification, not just an addition. (`URX` [51] and `UF` [52] KEEP their booleans: their rcd genuinely STAYS the shared `via_upstream` — the retry-limit final attempt is a real upstream 503, and the connect-failure rcd carries non-deterministic OS text — so those two flags remain boolean-derived. Only `UC`'s placeholder boolean is retired.)

envoy-rust on this path TODAY emits `rcd:"via_upstream"` (WRONG — Envoy emits `upstream_reset_before_response_started{connection_termination}`), so this phase corrects a real `%RESPONSE_CODE_DETAILS%` divergence and lights up the seventh rcd value, recon-confirmed, on a fully-built reset trigger.

## §2 — Scope (minimum-viable, ADR-0111)

**Set the deterministic reset rcd on the pure-reset path + migrate the `UC` flag onto it (retiring the redundant `reset_for_log` boolean) + a NEW `{rc,rcd,rf}` fixture reusing the phase-53 accept-then-close backend:**

- **§A — set the reset rcd on the pure-reset final-outcome path.** At the post-loop reconciliation region (`hcm.rs:~1200`, where phase 53 set `reset_for_log = matches!(final_outcome, Some(AttemptOutcome::Reset))`), set `response_code_details_for_log = Some("upstream_reset_before_response_started{connection_termination}".to_owned())` when the FINAL attempt's `AttemptOutcome` is `Reset` **AND `!retry_limit_exceeded_for_log`**. The `!retry_limit_exceeded_for_log` guard preserves the M53-3 edge: in the un-recon'd `retry_on:reset`-exhausted case (retry-limit-exceeded with a final reset), the rcd STAYS the shared `via_upstream` and the flag renders `URX` (the derive's URX branch is checked first) — exactly as today. The set OVERRIDES the `via_upstream` the proxy/synth arm wrote for the reset path; on a reset-retried-to-success (`final_outcome = Some(Response)`) the `matches!` fails → the rcd stays `via_upstream` → renders neither the new rcd nor `UC` (replay-safe per ADR-0044). ## §4 — Rejected / deferred

- **Amending fixture 0061 to add `rcd` (vs a NEW fixture 0062)** — rejected to keep 0061 a clean `{rc,rf}`-only byte-identical regression witness AND to follow the one-fixture-per-witness convention of the rcd/flag sub-family (0050/0053/0054/0055/0058/0056-0061 each added a NEW fixture; none amended a prior witness). 0062 reuses 0061's entire backend harness via the markers, so the marginal cost is one fixture dir + a thin test wrapper.
- **Keeping the `reset_for_log` boolean (purely-additive: set the rcd, leave the flag derive)** — rejected: once the rcd is unique, the boolean is redundant dead-weight (a reviewer Minor); migrating `UC` to rcd-derivation (the `UO` precedent) is the cleaner completion the phase-53 SPEC intended, and is output-equivalent on fixture 0061 (§3.1). The `!retry_limit_exceeded_for_log` guard keeps the M53-3 edge unchanged.
- **The downstream-termination `DC` flag** — requires a timing-dependent mid-request downstream disconnect (hard to drive deterministically); remains deferred (the `DC` slice of **M45-2**).
- **An upstream RST (vs the graceful FIN this phase uses)** — a hard RST (SO_LINGER 0) may render a different reset-reason brace; un-recon'd, out of scope (the FIN path is the clean deterministic `{connection_termination}`).
- **The BEHAVIOR_CONTRACT "(H1)" qualifier / H2-reset-still-502 note (M53-2)** — the §E edit touches the reset rcd/flag rows but M53-2 concerns the H2 reset STATUS path (`envoy-http2`), which this phase does not touch; left as a live carry-forward (fold whenever an H2 access-log differential driver lands — M45-1).
