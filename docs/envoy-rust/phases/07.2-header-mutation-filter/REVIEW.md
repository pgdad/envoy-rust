## §2. Strengths

1. **The `HeaderMutationFilter` runtime is exemplary minimal-scope design.** `crates/envoy-filter/src/header_mutation.rs` is well-factored: build-time lowering (`map_entry` translates the config-level `AppendAction` to the runtime `RuntimeAppendAction`, collapsing the 4-variant config enum to the 2-variant supported subset), build-time key lowercasing (the `key` field of `RuntimeHeaderMutation` is `to_ascii_lowercase()`'d once at `build_from_config` time, not per-request), and a tiny `apply_mutations` free function with clear RFC-7230-cited comments (`§3.2.2` for the list-valued Append semantic). The runtime struct holds `Vec<RuntimeHeaderMutation>` directly rather than `Arc<Vec<...>>` per 07.2 SPEC §6 signpost 3's YAGNI posture — correct for the 2-4-mutation fixture scale.

2. **The append/overwrite semantics are correct and exhaustively tested.** `apply_mutations` (`header_mutation.rs`) iterates `mutations` in slice (= YAML declaration) order per SPEC §6 signpost 8; `Append` pushes (allowing duplicates per RFC 7230 §3.2.2); `Overwrite` does a case-insensitive `retain` scan against the build-time-lowercased key, then pushes once. The 14-test Task 4 semantics inventory covers append-on-absent, append-on-present (duplicate), overwrite-on-absent, overwrite-on-present (exactly-one-entry), case-insensitive overwrite match, multiple-append-in-order, multiple-overwrite-last-wins, mixed append/overwrite ordering, empty-is-no-op on both decode and encode, `Continue` return on both sides, and two `FilterPipeline` round-trip tests proving the framework's declaration-order decode / reverse-declaration-order encode reach `HeaderMutation` correctly relative to the `Router` no-op terminus.

3. **The 9 H1/H2 HCM integration tests genuinely discriminate behavior.** `h1_decode_headers_fires_before_route_match` (and its H2 sibling `h2_decode_headers_fires_before_route_match`, strengthened in the Task 5 fix round to a real `HeaderMatcher`-gated route) use a route with no catch-all that matches only on a header the `HeaderMutation` decode-side mutation adds — a 200 "matched" response is *only* reachable if `decode_headers` ran before the route walk. That is a real discriminating test, not a smoke test. The `StopAndSend` tests (3, 4, 8, 9) exercise the framework's short-circuit on both decode and encode via the `test-util` stub filters. `h1_access_log_reflects_post_encode_headers` verifies the access-log dispatch site consumes the post-encode response state per parent-07 SPEC §6 Rule 8.

### Minor (awareness-only / track forward)

**M1. Severed `position` plumbing in `HttpFilterInstance::build` → `map_entry`.** `FilterPipeline::build_from_config` (`crates/envoy-filter/src/pipeline.rs`) correctly threads the filter-chain `position` via `.enumerate()` into `HttpFilterInstance::build`, but `build` (`crates/envoy-filter/src/instance.rs`) ignores it (`_position: usize`), and `map_entry` (`crates/envoy-filter/src/header_mutation.rs`) then hardcodes `position: 0` in the `FilterError::UnsupportedFilterType` it constructs for the defense-in-depth unsupported-`AppendAction` re-check. The plumbing exists end-to-end *except* the last two hops. **Why it matters:** D-3.4 stranger-readability — a future maintainer sees a `position` parameter threaded into a function that drops it, and a `position: 0` literal whose `0` is not the real value. This is **not a correctness bug**: the `envoy-config` validator (07.2 Task 2) is the operator-facing catch and it carries the correct entry index in `UnsupportedHeaderMutationAppendAction`; `map_entry`'s construction is defense-in-depth that only fires if a caller bypasses the validator. The Task 3 code-quality fix round already added a 4-line clarifying comment above the `position: 0` literal — that comment is fine; the residual smell is the dangling `_position` parameter that the comment does not address. **Fix sketch:** either (a) wire `position` through `build` → `build_from_config` → `map_entry` so the framework-boundary error carries a real value, OR (b) drop the `_position` parameter from `build` entirely and document that position-bearing errors are the validator's job. Option (b) is cleaner, is a ~2-line change, and is consistent with the 07.1 REVIEW I1 "delete dead plumbing" posture this same sub-phase just applied to `finalize_h2_stream`. **Disposition:** awareness-only; **close opportunistically** — fold into whichever future filter-family phase next touches `instance.rs::build` (the next non-HeaderMutation filter variant will re-open this surface). Named owner if closed deliberately: a future HTTP-filter-family phase. Does not gate the 07.2 state-6 close-out.

**M2. `apply_mutations` Overwrite is O(n²) in the (unlikely) many-entries case.** `crates/envoy-filter/src/header_mutation.rs` — each `RuntimeAppendAction::Overwrite` runs a full `headers.retain(...)` with a per-element `to_ascii_lowercase()` allocation. For 07.2's 2-4-entry fixtures this is correct and trivially cheap. 07.2 SPEC §6 signpost 3 explicitly defers the optimization per YAGNI ("If a future deployment lands a HeaderMutation with hundreds of entries, the planner refactors to `Arc<Vec<...>>` at that time"). **Why it matters:** purely a forward-looking performance note; no real-world hot path at 07.2 scale. **Fix sketch (if ever needed):** lowercase-compare without allocating (`eq_ignore_ascii_case`), or build a removal set once per `apply_mutations` call. **Disposition:** awareness-only, **carry forward indefinitely** — acknowledged-and-accepted YAGNI per the SPEC; no named owner; activates only if a future deployment surfaces large mutation lists.

**M3. Fixture 0013's `expected_body` byte-exact assertion is coupled to upstream Envoy's request-header injection set.** `tests/fixtures/0013-http-filter-header-mutation/expectations.yaml` hardcodes the exact echoed header set (`host`, `x-filter-stamp`) in `expected_body.body`. This relies on `tests/fixtures/0013-http-filter-header-mutation/envoy.yaml`'s `request_headers_to_remove` block enumerating *every* header Envoy v1.33 injects (the same 6-header list as fixture 0008). It is correct today — CI run `25887571566` is green — and matches the fixture-0008 precedent. **Why it matters:** a future Envoy version-pin bump (its own phase per D-3.7) that adds a new default request header would silently break the body-exact assertion until the `request_headers_to_remove` list is extended. The coupling is documented in the fixture `README.md` but not at the assertion site. **Fix sketch:** add a one-line comment in `expectations.yaml` cross-referencing the `request_headers_to_remove` list in `envoy.yaml` as the load-bearing coupling. **Disposition:** awareness-only documentation polish; **close opportunistically** — fold into any future task that touches fixture 0013 or the Envoy version-pin bump phase (whichever re-baselines the differential suite). Named owner: the future `ENVOY_TARGET.md` version-bump phase is the natural forced-close site.
