## 1. Summary

Phase 04.1 lands the foundational HTTP/1.1 surface for envoy-rust: a brand-new `envoy-http1` library crate that owns the workspace's sole runtime dependency on `httparse` (per parent-04 SPEC §3 cross-sub-phase rule 1), an HCM `ConnectionHandler` impl that walks an inline `RouteConfiguration` first-match-wins on Host then path, a hardcoded router-filter call site that emits `direct_response` actions, and the harness extensions to drive `Driver::Http1` with set-equal-modulo-allow-list response-header equivalence. The implementation reads as a careful continuation of phase 03.x's posture rather than a re-architecture: every doctrinal axis, every public-surface boundary, and every harness invariant from earlier phases is preserved unchanged. The new crate ships with `#![forbid(unsafe_code)]` (`crates/envoy-http1/src/lib.rs:1`), a tight error taxonomy (`error.rs` — 6 variants with explicit `From<std::io::Error>` for `?`-ergonomic propagation), case-insensitive header lookup with case-preserving storage (`headers.rs` — 6 canonical lowercase constants + `find_header` helper), a hand-rolled IMF-fixdate writer via Howard Hinnant's civil-from-days algorithm (`date.rs` — `format_imf_fixdate` + 2 RFC-canonical-example tests pinning `Sun, 06 Nov 1994 08:49:37 GMT` + Unix-epoch boundary), a thin `httparse::Request::parse` wrapper enforcing 8 KiB headers cap and exhaustive `httparse::Error` variant mapping (`codec.rs` — `Http1Codec::parse_request` + `Request` + `HttpVersion` enum + 5 unit tests), a dumb wire-format response writer with built-in canonical-reason table covering 24 RFC 7231 §6.1 codes (`response.rs` — `Http1Response::write_to` + `Response` + 2 byte-exact tests), and the heart of the phase, `hcm.rs` — `HCM` + `HCMConfig` + `serve_connection` per-connection state machine + route walker + `synth_*` helpers + 8 unit tests covering direct-response happy-path, host-port stripping, first-match-wins on routes, missing-Host → 400, unknown-route → 404, `Connection: close` socket close, keep-alive serving two requests on one connection, and `Transfer-Encoding: chunked` → 501.

envoy-config grows by exactly the 10 new types, the 10 new `ConfigError` variants, the 1 new `HCM_FILTER` const, and the 3 validator helpers (`validate_hcm`, `validate_data_source`, `is_valid_dns_name`) that SPEC §3 D2 enumerates. ## 2. Strengths

- **Doctrine conformance end-to-end.** `#![forbid(unsafe_code)]` at line 1 of `crates/envoy-http1/src/lib.rs` (the only new crate root in the phase). Zero new dep additions to the allow-list; the new `envoy-http1` crate's deps (`httparse`, `bytes`, `tokio`, `thiserror`, `tracing`) are all pre-existing permitted foundations. Append-only ADR ledger preserved exactly (`git diff 1d9740d..05a5f23 -- docs/envoy-rust/DECISIONS.md` empty; ADR-0001–0020 byte-identical). Toolchain pin untouched. Envoy version pin untouched.

- **`Http1Codec::parse_request` is a textbook httparse wrapper with exhaustive error-variant mapping.** `crates/envoy-http1/src/codec.rs:53-77` covers all 7 of httparse 1.10.x's `Error` variants explicitly (`HeaderName | HeaderValue | NewLine | Status` → `MalformedHeader`; `Token | Version` → `MalformedRequestLine`; `TooManyHeaders` → `HeadersTooLarge { cap: 8192 }`). PROGRESS Task 8 documents the registry-source verification (`~/.cargo/registry/src/index.crates.io-.../httparse-1.10.1/src/lib.rs:102-117`) — strictly more rigorous than a wildcard `_ => MalformedHeader` arm. The 8 KiB headers cap is enforced both on `Status::Partial` (`buf.len() > HEADERS_CAP`) and on the explicit `TooManyHeaders` variant — defense-in-depth against attackers crafting a request with 65 header rows (httparse defaults `MAX_HEADERS = 64`) all under the byte cap.

**M1. `diff_headers` value-comparison uses `find()` and so silently ignores duplicate-header value mismatches.** *(Awareness-only.)*

`tests/differential/src/lib.rs:200-209` looks up each side's value via `iter().find(|(n, _)| n.eq_ignore_ascii_case(name))`, returning the *first* matching row. If a future fixture's response carries duplicate header rows (e.g. two `Set-Cookie` rows with different values), the duplicates after the first will not be diffed. For 04.1 this is non-bug — fixture 0007's HCM-direct-response output has no duplicate headers (the 5 emitted headers — `server`, `date`, `content-length`, `content-type`, `connection` — are unique by RFC). Phase 04.2 (header matchers) and phase 04.3 (upstream proxying) may surface fixtures where the upstream emits duplicate headers (e.g. cookies, `Vary`); at that point the `find()` form should evolve to `filter().collect::<Vec<_>>()` and an ordered-multiset comparison.

*Fix:* leave as-is for 04.1. Track forward into 04.2 when header matchers may need duplicate-header semantics.

**M2. The `_elapsed` arm in the body-drain timeout returns `Ok(())` rather than surfacing an error.** *(Awareness-only.)*

`crates/envoy-http1/src/hcm.rs:167` returns `Ok(())` on idle-timeout-during-body-drain, dropping the pending response. PROGRESS Task 10 review-fix subsection lines 132-134 names this as a known divergence ("matches PLAN reference; the 5s idle-read timeout in the body-drain loop returns `Ok(())` rather than surfacing an error"). Phase 04.3 (upstream proxying with non-trivial bodies) may need the slow-body-attack mitigation to surface as a typed error rather than a silent close.

*Fix:* leave as-is for 04.1; revisit in 04.3 or hardening pass when body-drain semantics first matter.

**M4. `strip_port` is `rfind(':')` which is incorrect for bare-IPv6 Host (no port).** *(Awareness-only.)*

`crates/envoy-http1/src/hcm.rs:246-251` does `host.rfind(':').map(|i| &host[..i]).unwrap_or(host)`. For `Host: [::1]` (bare IPv6, no port), `rfind(':')` returns the position of the last `:` *inside* the brackets, slicing to `"[::"`. The validator's `is_valid_dns_name` (`bootstrap.rs:673-689`) does not accept `:` in domain matchers, so any IPv6-Host request would walk to `synth_404` regardless — the bug is unobservable for valid configs. But a future fixture mixing a `*` catch-all VH with an IPv6-Host request would 404 silently rather than match (because the stripped Host `"[::"` is then matched against `*`, which always matches — so actually it would 200, but with the wrong Host string in any future debug logs). Defense-in-depth would be `if host.starts_with('[') && let Some(end) = host.rfind(']') { /* IPv6 with optional port */ } else { /* legacy rfind */ }`.

*Fix:* leave as-is for 04.1. Track forward into 04.3 (upstream proxying may surface IPv6 backends; if the Host gets forwarded, the strip would matter); a full IPv6-Host fixture would be the right place to land the tightening.

**M7. HCM+TLS detect-and-bail is in 04.1 but the architectural seam (`TlsAcceptingHandler.inner: Arc<TcpProxy>`) needs generalization for phase 05+.** *(Tracked forward.)*

`crates/envoy-bin/src/tls_handler.rs:13-16` types the `inner` field as `Arc<TcpProxy>` (concrete) by design — the inherent-generic `handle::<S>` precedent keeps `ConnectionHandler` object-safe with a concrete `TcpStream`, and the adapter calls `inner.handle::<TlsStream<TcpStream>>` directly via `Arc<TcpProxy>` (cannot `dyn`-call a generic method). Wrapping HCM in `TlsAcceptingHandler` would not typecheck; the 04.1 dispatch arm at `crates/envoy-bin/src/main.rs:230-236` detects-and-bails with a clear error message. Phase 05+ (HTTP/2 with TLS, mTLS) will need to generalize this. Two options surface:

(a) Make `TlsAcceptingHandler.inner: Arc<dyn ConnectionHandler>` and add a parallel `handle_post_handshake::<S>` method on the trait taking a `TlsStream<TcpStream>` (breaks object-safety unless the trait's method also stays concrete on a boxed type — possible via `Box<dyn AsyncReadWrite + Send + Unpin>`).

(b) Build a parallel `TlsAcceptingHcmHandler` that mirrors `TlsAcceptingHandler` but with `inner: Arc<HCM>` — duplicates ~30 LoC but stays within the existing trait shape.

(c) Replace the inherent-generic `handle::<S>` with a fully-erased boxing arm at the trait level (`handle(&self, downstream: Box<dyn AsyncReadWrite + Send + Unpin>)`), unifying both `TcpProxy` and `HCM` under one trait method — this is the most invasive but most extensible option.

*Fix:* leave as-is for 04.1. Track forward into phase 05's brainstorm; the choice between (a) / (b) / (c) is a design decision that depends on whether HTTP/2 lands its own `Http2Connection` ConnectionHandler shape.
