## Named focus-item verdicts (all PASS)

1. **The byte-exact `JwtError`→(status, body, `www-authenticate`) wire map — PASS.** All 10 failure-class body literals (`jwt_authn.rs:205-245`) are byte-exact against the ADR-0056 §6.2 L2 table and the BEHAVIOR_CONTRACT "22 entries" block — independently byte-counted (Missing 14 / NotInForm 79 / BadHeaderJson 29 / BadPayloadJson 30 / NoMatchingKey 50 / VerificationFails 22 / IssuerMismatch 28 / Expired 14 / NotYetValid 17 / AudienceNotAllowed 32), every one matches. `JwtError::AudienceNotAllowed` is the SOLE 403 (`jwt_authn.rs:230`); the reason phrase derives purely from `status == 403` → `Forbidden` else `Unauthorized` (`:235-239`). The L3 dynamic realm is `format!("http://{host}{path}")` with a case-insensitive verbatim `Host` lookup (`:174-177`); `www_authenticate` omits `error=` only for the Missing class and includes `, error="invalid_token"` for all others (`:196-203`). `BEHAVIOR_CONTRACT.md:383-404` matches the code literals byte-for-byte — no doc/code drift.
2. **The RS256 verify orchestration (`verify.rs:62-136`) — PASS.** The production verify path is exactly the §6.2-L1-locked `PublicKeyComponents { n, e }.verify(&RSA_PKCS1_2048_8192_SHA256, signing_input, &sig)` — direct from the raw big-endian modulus/exponent, NO DER assembly, NO feature flag, no `unsafe` (`verify.rs:104-112`). Leading-`0x00` strip applied to BOTH `n` and `e` at JWKS parse time (`jwks.rs:65-66`). The 10-check order is faithful: form → header decode/JSON → payload decode/JSON → sig decode → alg≠RS256→NoMatchingKey → key-select by kid/all → verify→VerificationFails → issuer → exp-before-nbf → audience(empty-skip). The signing-input slice `&token.as_bytes()[..h.len()+1+p.len()]` (`verify.rs:104`) is provably in-bounds: the 3-segment match (`:71-76`) guarantees three non-empty single-`.`-separated substrings, so `h.len()+1+p.len()` is the byte offset of the second dot, strictly `< token.len()` because the non-empty `s` follows — no panic, no mid-char split (all-ASCII boundary). Unit tests sign REAL RSA-2048 tokens via the aws-lc-rs signing helper and exercise every failure class.
3. **The base64url non-canonical tolerance (`base64url.rs:6-29`) — PASS (benign for production).** The hand-rolled decoder accepts a final base64url quantum whose discarded low bits are non-zero (it does not reject `"…B"` vs `"…A"` where only the unused bits differ) — this is correct/standard and matches Envoy. Accepting a re-encoded VALID signature is NOT a forgery (the re-encoding decodes to the identical signature bytes, which is what was already signed), so the production verify path is unaffected. This non-canonical tolerance was the root cause of the state-4 flaky-tamper TEST (see focus item 5); it is a benign decoder property, not a verification weakness. The decoder is panic-free on all input lengths (0/1/2/3 mod 4; empty; single char) — pure-accumulator, no indexing/slicing.
4. **`forward`-default-strips-`Authorization` (L6) + no-matching-rule-ALLOW (L4) — PASS.** On a verified (success) request the `Authorization` header is removed from the `FilterRequest` via a case-insensitive `retain` iff `!forward` (`jwt_authn.rs:170-172`); `forward: true` keeps it (the provider `forward` field defaults `false`, `bootstrap.rs:730`). Both directions are unit-tested. A request matching NO `rules[]` entry returns `Decision::Continue` and increments `allowed` (`jwt_authn.rs:103-112`) — the §6.2 L4 pass-through. Stats: `allowed` ticks on BOTH no-rule pass-through AND verify-success; `denied` on every 401/403; each path increments exactly one counter once (no double-count), at the `http.<hcm_stat_prefix>.jwt_authn.{allowed,denied}` namespace (`:89-99`).
5. **The state-4 tamper fix (`04b9e97c4`) — PASS.** The fix replaces the flaky last-sig-char tamper (which carried only 2 meaningful bits of a 256-byte RSA signature → a ~20% no-op for random keys → the "tampered" token still verified) with a deterministic FIRST-sig-char flip (`sig_start = rfind('.')+1`; `'B' if char=='A' else 'A'`), applied consistently at all three runtime sites: `crates/envoy-filter/src/jwt_authn.rs`, `crates/envoy-jwt/src/verify.rs`, and the fixture generator `tests/fixtures/0030-…/inputs/gen.sh:59-65`. The production verify path + the lenient decoder are UNCHANGED and correct. Verified 0/250 failures on each fixed test post-fix.

### Minor (Nice to Have)

- **M22-1 (cluster A).** `base64url::decode` (`crates/envoy-jwt/src/base64url.rs:6-29`) accepts an input whose length ≡ 1 mod 4 (e.g. `"A"`) as `Ok(...)` with the leftover 6 bits silently dropped, rather than erroring — RFC 4648 produces no valid encoding ending in a single leftover sextet. It is panic-free and differentially harmless (a 1-mod-4 header/payload still has to JSON-parse and a 1-mod-4 signature still has to RSA-verify, both of which fail downstream — it cannot leak a forged token), but if exact-match with Envoy's per-segment base64 reject is ever asserted, add `if s.len() % 4 == 1 { return Err(()) }`. No correctness/security impact.
- **M22-2 (cluster B).** The route-match exactly-one-of check is inlined in `validate_jwt_authn_config` (`bootstrap.rs:2945-2960`) rather than sharing a helper with the equivalent inline check in `validate_http_connection_manager` (~`:2543`) — the code carries an explicit comment noting the duplication. A future refactor to a shared `validate_route_matcher` helper would prevent drift between the two sites. Cosmetic.
- **M22-3 (cluster C).** The Host-absent realm fallback (`jwt_authn.rs:174-177`, `header_ci(...).unwrap_or("")`) yields `http://{path}` (e.g. `http:///` for path `/`). Panic-free and sane, but the empty-Host wire shape is unverified against real Envoy (the differential fixture 0030 always drives a fixed `Host: envoy.test`, so it is never exercised). Out-of-fixture-scope; no action at this scope.
- **M22-4 (cluster C).** `realm()` uses `req.path` verbatim including any query string (`jwt_authn.rs:115`), consistent with the contract's "the request path"; the fixture drives path `/`, so query-string realm handling is untested. Out-of-fixture-scope.
- **M22-5 (cluster D).** The committed `tests/fixtures/0030-…/inputs/tampered.jwt` (and the byte-identical backstop `TAMPERED_JWT` const) is the LEGACY last-sig-char-flip artifact (it differs from `valid.jwt` only at the final sig char `…HGjRSQ`→`…HGjRSB`, decoded sig byte 255 `0x49`→`0x48`), NOT the first-char flip that the state-4-fixed `gen.sh` now regenerates. For THIS committed key the byte-255 flip DOES deterministically break verification — proven GREEN on Linux CI run `27179560746` (`http_filter_jwt_authn_fixture … ok`, both proxies 401 verify-fails byte-identical) + the passing backstop probe-3 — so it is NOT a correctness defect. But the committed artifact no longer matches its generator: a future regeneration would silently change `tampered.jwt` to the first-char variant. Recommended follow-up: regenerate the full token set with the fixed gen.sh so the committed artifact matches its generator (and removes the regeneration footgun). No correctness/security impact today.
- **M22-6 (cluster D).** `tests/fixtures/0030-…/expectations.yaml:11` still comments "last sig char flipped" — accurate for the currently-committed token (M22-5) but inconsistent with gen.sh's now-first-char comment. Update together with M22-5 if regenerated.
- **M22-7 (cluster D).** The `jwt_parse` fuzz corpus seed `crates/envoy-jwt/fuzz/corpus/jwt_parse/jwks.json` uses a SPACE to separate the JWKS from the token, but the fuzz target splits on NUL (`\0`) — so this seed is consumed entirely as the (now-invalid) JWKS string and `verify_rs256` is never reached from it (only the `token.txt` seed, which starts with a `0x00`, exercises the both-surfaces path). Corpus-coverage quality only — no safety impact (the target still cannot panic; 6.7M runs/0 crashes). Recommended: replace the space with a NUL so both seeds reach `verify_rs256`.

**Confirmed-correct observations (NOT findings).** (a) `verify_rs256` returns `IssuerMismatch` when the token has NO `iss` claim at all (`verify.rs:117`, `claims.iss.as_deref() != Some(expected_issuer)`) — this is the intended behavior (a missing required issuer is the same failure class in Envoy; the `VerifiedJwt.iss` doc at `verify.rs:16` documents it). (b) `error.rs`'s `Display` strings are NOT the load-bearing wire bytes — the byte-exact bodies are emitted at the mapping site `jwt_authn.rs:217-245`; the `JwtError` taxonomy supplies only the variant identity, which maps cleanly.
