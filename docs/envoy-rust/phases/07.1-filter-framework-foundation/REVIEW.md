2. **`Decision::{Continue, StopAndSend(FilterResponse)}` scaffolding from day one is correct forward-compat.** `crates/envoy-filter/src/pipeline.rs:7-11` defines the enum with both variants at Task 2, even though no 07.1 filter emits `StopAndSend` (Router is a no-op terminus). The HCM wiring at H1 (`crates/envoy-http1/src/hcm.rs:370-378` decode-side, lines 576-585 encode-side) and H2 (`crates/envoy-http2/src/hcm.rs:175-184` decode-side, lines 475-483 encode-side) both handle the StopAndSend arm structurally — unreachable under the Router-only 07.1 chain but lit by 07.2's HeaderMutation without retrofit. Forward-compat scaffolding only; does not violate the "don't design for hypothetical future requirements" doctrine because 07.2 is concretely projected in the immediately-following sub-phase.

3. **Iteration-order semantics match parent-07 SPEC §6 Rule 6 verbatim.** `crates/envoy-filter/src/pipeline.rs:41-49` (decode) walks `self.filters.iter_mut()` — declaration order; `crates/envoy-filter/src/pipeline.rs:58-66` (encode) walks `self.filters.iter_mut().rev()` — reverse declaration order. Inline doc-comments at lines 37-40 + 51-57 narrate the Envoy v1.33 semantic ("Router produces the response so it fires first on encode"). The `RouterTerminus::decode_headers` and `RouterTerminus::encode_headers` no-op design at `crates/envoy-filter/src/router.rs:28-34` correctly models "Router is terminal but does NOT terminate the filter chain" — the iteration walks Router last on decode and first on encode, but the actual route-match / dispatch happens inside the HCM's writer-arm match after `pipeline.decode_headers` returns. This is doctrinally tight: the filter-chain-level Router is a no-op; the HCM-level Router is the dispatcher.

5. **The Cargo cycle resolution (Task 5.5 / ADR-0031) is the cleanest minimal-scope option.** Parent-07 SPEC §5 signpost 7 + 07.1 PLAN architecture decision 7 specify the dep stack `envoy-config → envoy-filter → envoy-http1, envoy-http2 → envoy-bin` with `envoy-filter` depending on `envoy-http1` for `codec::Request` / `Response` value types AND the reverse direction. ### Important (close in 07.1 or carry forward with named owner phase)

**I1. Task 7 `finalize_h2_stream` 3-dead-parameter design smell.** The post-encode shadowing approach at `crates/envoy-http2/src/hcm.rs:451-453` leaves three pre-encode parameters (`_response_status_for_log: u16`, `_response_body_len: u64`, `_response_headers_for_log: &[(String, String)]`) on the signature whose values are unconditionally discarded by the function body. Inside `finalize_h2_stream`, lines 490-493 derive `response_status_for_log: u16 = resp.status`, `response_body_len: u64 = resp.body.len() as u64`, and `response_headers_for_log_owned: Vec<(String, String)> = resp.headers.clone()` from the post-encode `resp` value (after the `pipeline.encode_headers(&mut filter_resp)` call at line 468 has run). The pre-encode values are computed at each of the 3 callers (`handle_one_stream` at lines 199-201 / 222-224 / 318-320 / 391-393 / 401-403 — five sites populating the trio, three of which then call `finalize_h2_stream` passing the trio at lines 236-238 / 332-334 / 417-419) and then unconditionally thrown away. **Why it matters:** D-3.4 stranger-readability — a future maintainer reading `finalize_h2_stream`'s signature sees three parameters with `_` prefixes and a body that shadows them; the cognitive overhead is high and the parameters are misleading scaffolding. The `clippy -D warnings` posture is preserved by the underscore-prefix trick, but the result is a function signature carrying ~12 lines of dead code spread across the 3 caller sites + the function itself. **Fix sketch (Option B per the Task 7 code-quality reviewer's recommendation):** remove the 3 parameters entirely from `finalize_h2_stream`'s signature; have all 3 callers stop computing the pre-encode trio (eliminates the 5 sites in `handle_one_stream` that populate `response_status_for_log` / `response_body_len` / `response_headers_for_log` before passing them along); `finalize_h2_stream`'s body unconditionally computes all 3 from `resp` post-encode (the current shadow body already does this — just drop the parameters). Estimated ~12 line removals across `handle_one_stream` + the function signature; zero behavior impact. **Disposition:** **carry forward to 07.2 Task 5 cleanup.** 07.2 Task 5 is the first task that adds a non-Router filter (HeaderMutation) and will touch the H2 HCM's filter-invocation surface naturally; folding the cleanup into that task's PLAN-write at 07.2 state-2 is cheaper than a separate state-5 fixup commit in 07.1. The mechanical change is small enough that it does not warrant blocking 07.1's state-6 close-out. Alternative dispositions considered: (a) close in 07.1 via a state-5 fixup commit before state-6 — rejected because the 12-fixture-green state-4 anchor is already complete and a fixup commit would force a re-run of the state-4 gate; (b) accept as awareness-only M-track — rejected because the design smell is more than cosmetic (it actively misleads readers about the function's parameter contract). **Carry forward to 07.2 Task 5** as the named owner; record explicitly in §7 below.
