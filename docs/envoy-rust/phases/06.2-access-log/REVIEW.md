### Important (close in 06.3 or carry forward with named owner phase)

**I1. The H1 access-log state vars are initialized with `mut x = 0` defaults rather than the H2 path's `let x;` posture, defeating Rust's all-paths-write enforcement.** `crates/envoy-http1/src/hcm.rs:313-316`:

```rust
let mut response_status_for_log: u16 = 0;
let mut response_body_len: u64 = 0;
let mut upstream_host_for_log: Option<String> = None;
let mut response_headers_for_log: Vec<(String, String)> = Vec::new();
```

Compare to H2 at `crates/envoy-http2/src/hcm.rs:134-137`:

```rust
let response_status_for_log: u16;
let response_body_len: u64;
let response_headers_for_log: Vec<(String, String)>;
let mut upstream_host_for_log_h2: Option<String> = None;
```

The H2 posture is strictly stronger: Rust's flow analysis requires every match arm to write the uninitialized locals before they're read. The H1 posture silently defaults to `response_code: 0` + `bytes_sent: 0` + empty `Vec` if a future code path (e.g., a panic-safe early-return; a new outcome variant; a refactor that adds an `if let` short-circuit) bypasses a writer. PROGRESS Task 7 deviation 4 acknowledges this asymmetry — "*Minor style asymmetry vs the H1 path where all 4 are `mut`; documented here so reviewers don't flag it.*" — but the style decision deserves a tightening pass: prefer H2's posture. Mechanical fix: drop the `mut` and the `= 0` / `= None` / `= Vec::new()` defaults on the H1 site; verify all 5 H1 writer arms still type-check. **Disposition:** carry forward to 06.3 or absorb in whichever phase next touches `crates/envoy-http1/src/hcm.rs:319-457`'s match block.

**I2. The fixture-vs-contract User-Agent disposition divergence is not surfaced in BEHAVIOR_CONTRACT.md, and PROGRESS's rationale is empirically wrong.** Fixture 0012's `tests/fixtures/0012-access-log-file-sink/expectations.yaml` uses `rule: wildcard` for the `%REQ(USER-AGENT)%` token slot, but `docs/envoy-rust/BEHAVIOR_CONTRACT.md:138` declares the canonical disposition as `value-exact` with rationale "*Same rationale as %REQ(X-FORWARDED-FOR)%*". PROGRESS Task 10 deviation 2 explains the divergence as: "*`drive_http1` (the 04.1 helper) sets `User-Agent` to a default*". But `tests/differential/src/lib.rs:832-855` shows `drive_http1` does NOT inject any `User-Agent` header — its request builder writes only `<METHOD> <PATH> HTTP/1.1\r\nHost: <host>\r\n`, then iterates `extra_headers`, then appends `Connection: close\r\n\r\n`. No User-Agent path. Either (a) the wildcard is hiding a real envoy-vs-envoy-rust divergence (e.g., upstream Envoy emits some default User-Agent that envoy-rust doesn't, or vice versa), or (b) `wildcard` is unnecessarily loose and the rule should tighten to `exact: "-"`. The reviewer cannot determine which from the in-tree artifacts. **Disposition:** carry forward to 06.3 — diagnose empirically (run the fixture once with `exact: "-"` and observe the failure mode, OR add a logging tap to capture what each proxy sees for User-Agent). If (a), update BEHAVIOR_CONTRACT.md row 12 with the actual divergence rationale; if (b), tighten fixture 0012's expectations.yaml to `exact: "-"`. PROGRESS Task 10 dev 3 already acknowledges the contract-vs-fixture-rule split, but the rationale text in PROGRESS itself is wrong; the gap should not persist past 06.3.

### Minor (awareness-only / track forward)

**M1. The `Http1Error::AccessLogOpen` variant wraps the underlying `AccessLogError` as `message: String`, losing source-chain typing.** `crates/envoy-http1/src/error.rs` declares `AccessLogOpen { message: String }` with `#[error("failed to open access log sink: {message}")]`. PROGRESS Task 6 dev 2 explains: thiserror treats a field named `source` as a nested `std::error::Error` and `String` doesn't implement `Error`. The fix preserves a working `Display` but loses the typed-error-source chain — `err.source()` returns `None` for `AccessLogOpen`. The 06.1 `StatsRegistration { stat_prefix, message: String }` precedent (PROGRESS Task 6 cites it explicitly) has the same shape. **Fix sketch:** make the inner an `AccessLogError` directly with `#[source]` (`AccessLogError` is `thiserror::Error` so it satisfies `std::error::Error`); use a named non-`source` field `inner: AccessLogError` with the explicit `#[source]` attribute (per thiserror docs). Both restore source-chain traversal. ~5 LoC at one site. Defer; consistent with the 06.1 precedent for now.

**M2. The `BodyRule::ByteExact` body-rule does not assert against a literal expected body.** `tests/fixtures/0012-access-log-file-sink/expectations.yaml` declares `expected_body: { kind: byte_exact }`. Per `tests/differential/src/lib.rs::assert_body_rule`, `BodyRule::ByteExact` only enforces byte-equality between upstream Envoy and envoy-rust — it does NOT assert either body actually equals `"ok\n"`. A future regression that breaks BOTH proxies symmetrically (e.g., a `direct_response` body bug that swallows the inline_string entirely) would pass the fixture's body check. The 04.1 / 04.3 / 05.2 / 05.3 fixtures all use the same shape, so this is pre-existing — but the access-log fixture's `BYTES_SENT` token IS asserted as `exact: "3"`, which would catch that regression via the token rule, not the body rule. The surface is covered by belt-and-braces in 06.2 but the pattern is fragile. **Fix sketch:** introduce `BodyRule::ByteExactValue { value: String }` (mirrors `Http1BodyRule::ByteExact { body: String }` that already exists for the legacy 04.x driver) and let fixtures opt in to a literal-value assertion. Defer; phase-wide pre-existing pattern, not 06.2-specific.

**M3. Fixture 0012's `README.md` documents the pre-CI-fix access-log paths.** `tests/fixtures/0012-access-log-file-sink/README.md` lists `/tmp/0012-envoy-access.log` and `/tmp/0012-envoy-rust-access.log`, but the actual `envoy.yaml`, `envoy-rust.yaml`, and `expectations.yaml` use `/tmp/0012-envoy-mount/access.log` and `/tmp/0012-envoy-rust-mount/access.log` (the parent-directory-bind-mount form from CI-fix commit `4aba10b`). A stranger reading the README to understand the fixture sees inconsistent paths. **Fix sketch:** edit README.md to match the post-CI-fix paths; add a one-line note explaining the parent-dir mount strategy and cross-reference Task 10's CI-fix in PROGRESS. ~5 LoC of doc edit. Defer to 06.3 or fold into a 06.3-task that touches the fixture.

**M4. `/tmp/0012-envoy-mount/` is a process-shared host path; parallel `cargo test` jobs could collide.** `tests/differential/src/lib.rs:1388-1431` extracts the parent dir from the fixture's `expected_access_log_paths` and creates+chmods it host-side under `/tmp/0012-envoy-mount`. If two CI jobs (or two local test runs) execute fixture 0012 simultaneously, they'd race on the same parent directory and could overwrite each other's `access.log`. Today the testcontainers harness implicitly serializes Docker-gated tests (each fixture acquires the container's exposed port and tears down at drop), so the collision is mostly hypothetical — but the path being hardcoded means a future parallelism push (e.g., `cargo nextest`'s test sharding) would surface this. **Fix sketch:** prefix the access-log directory with a process-PID or per-fixture tempdir (`/tmp/0012-envoy-mount-{pid}/`), template-substitute into the YAML at fixture-render time. ~15 LoC. Defer to whichever phase first parallelizes Docker-gated tests (likely a CI-infra phase post-08).

**M5. The H2 access-log test settles via a 200ms `tokio::time::sleep` rather than awaiting the connection task.** `crates/envoy-http2/src/hcm.rs` test fixture sleeps for 200ms because "*the H2 conn future does not return until the server side EOFs the TCP stream*" (PROGRESS Task 7 deviation 3). Acceptable for a unit test today but adds CI runtime + potential flakiness on a loaded runner. **Fix sketch:** use `h2::server::SendResponse::stream_id()` / a `Notify` shared between the test and the server task to deterministically signal emission completion. ~30 LoC. Defer; pattern-equivalent to the 06.1 backstop's `thread::sleep(100ms)` posture (M5 from 06.1 REVIEW chain).
