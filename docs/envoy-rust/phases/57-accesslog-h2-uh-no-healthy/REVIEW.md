## Findings

### Minor 1 (informational — no action required) — `synth_h2_no_healthy_upstream()`'s header set omits `content-length`, unlike its own sibling helper

`crates/envoy-http2/src/hcm.rs` (`synth_h2_no_healthy_upstream`, near the Task-1 insertion point): the new helper has a non-empty 19-byte body but its header set (`server`, `content-type`) omits `content-length`, unlike its own sibling non-empty-body H2 synth helper `synth_h2_overflow()`, which does include `content-length` for its body. Internally inconsistent with the established pattern for non-empty-body H2 synths in this same file, though not incorrect per HTTP/2 framing rules (END_STREAM signals body end without `content-length`) and explicitly out of the differential fixture's asserted surface (status + access-log line only, not headers/body). Low risk; worth a one-line follow-up (`("content-length".to_string(), body.len().to_string())`) whenever this arm is next touched, for consistency with `synth_h2_overflow`. Not worth a dedicated task.

### Minor 2 (informational — no action required) — doc comment oversells header parity with the H1 precedent

The doc comment on `synth_h2_no_healthy_upstream` says it "mirrors `envoy_http1::hcm::synth_no_healthy_upstream` exactly" for status/body, but the H1 version actually emits 5 headers (`server`, `date`, `content-length`, `content-type`, `connection`) vs. the H2 version's 2 — "exactly" oversells the header parity, though the surrounding sentence correctly scopes the claim to "status 503, body byte-exact" only. Purely a comment-wording nit; not misleading in context once read fully. Not worth a fix.
