# Phase 51 — `51-accesslog-rf-retry-exhausted` — SPEC

**Pick (ADR-0108):** differentially WITNESS the **FOURTH non-`-` `%RESPONSE_FLAGS%` value — `URX` (UpstreamRetryLimitExceeded)** — BYTE-EXACT on the H1 retry-limit-exceeded path (`retry_policy: {retry_on:"5xx", num_retries:N}` where every attempt returns a retriable 5xx so the retry budget of `N` is consumed and the LAST upstream response is returned downstream VERBATIM — ADR-0045 finding L9), by (i) setting a NEW per-request boolean `retry_limit_exceeded_for_log = true` at envoy-rust's retry-loop limit-exceeded exit (`crates/envoy-http1/src/hcm.rs:1126`-`1128`, the EXACT site where `upstream_rq_retry_limit_exceeded().inc()` fires — `attempts > 1 && !retry_budget_blocked && final_retriable`), and (ii) extending the phase-48/49/50 `%RESPONSE_FLAGS%` derive at `crates/envoy-http1/src/hcm.rs:1274` to render `"URX"` when that boolean is set (today the derive maps only the rcd strings `route_not_found => "NR"`, `no_healthy_upstream => "UH"`, `upstream_reset_before_response_started{overflow} => "UO"`, else `"-"`). The `%RESPONSE_FLAGS%` continuation after `NR` (phase 48) + `UH` (phase 49) + `UO` (phase 50) onto the FOURTH already-implemented failure path. The fifteenth Observability access-log row.

> **State-0 recon — the make-or-break design finding (this session, folded):** unlike `NR`/`UH`/`UO`, the retry-exhausted path's `%RESPONSE_CODE_DETAILS%` is **`via_upstream`** — the SAME string a normal successful upstream response carries — NOT a unique rcd. Live `envoyproxy/envoy:v1.33.0` (digest `sha256:56da5afd…`, host Docker `-p` port-mapping), the `0024` `/retry-exhausted` topology (`retry_policy:{retry_on:"5xx",num_retries:1}`, a backend that 503s every attempt) with a `{rc,rcd,rf}` `json_format` access-log, driven by `GET /retry-exhausted`, emits — byte-stable across repeats — `{"rc":503,"rcd":"via_upstream","rf":"URX"}`. **Two consequences:** (a) envoy-rust ALREADY emits `rcd:"via_upstream"` on this path (the final attempt is a real upstream 503 → the writer arm `hcm.rs:866`/`:1019-1023` keeps `via_upstream`), so this phase needs **NO `%RESPONSE_CODE_DETAILS%` change** — it matches Envoy byte-exact today; (b) the `%RESPONSE_FLAGS%` derive therefore **CANNOT be rcd-driven** (`via_upstream` is shared with every success → an rcd arm would mis-flag every 2xx as `URX`). `URX` requires a **separate boolean discriminator** threaded from the retry-limit-exceeded loop-exit — the genuinely new mechanism this phase introduces (phases 48/49/50 all reused the rcd-match; this is the first `%RESPONSE_FLAGS%` value NOT 1:1 with a unique rcd).

## §1 — Why this pick

`%RESPONSE_FLAGS%` already renders in all three encoders (`default_format.rs:60`, `json_format.rs:242`, `command_operator.rs:526`); phase 48 (ADR-0105) made the field per-request via the derive at `hcm.rs:1274`, phase 49 (ADR-0106) added `UH`, phase 50 (ADR-0107) added `UO`. `URX` is the cheapest next flag onto an already-built, already-green failure path:

- **The retry-limit-exceeded path is already implemented and already differentially green.** envoy-rust's H1 retry loop (phase 16, ADR-0044/0045) drives `retry_policy:{retry_on,num_retries}`; when the budget of `num_retries` is consumed and the final attempt is still retriable, the LAST upstream response is returned downstream verbatim (L9) and `upstream_rq_retry_limit_exceeded` ticks at `hcm.rs:1128`. Fixture `0024-upstream-retry-on-5xx` (phase 16) ALREADY proves that path byte-exact cross-proxy on the `/retry-exhausted` probe (both attempts 503, retry consumed, last 503 `"service unavailable\n"` returned verbatim, `x-envoy-attempt-count: 2`). No new trigger surface, no new retry mechanism — only the access-log `%RESPONSE_FLAGS%` rendering is unbuilt (and currently WRONG: it renders `rf:"-"`).
- **State-0 recon-CONFIRMED at `envoyproxy/envoy:v1.33.0`** (this session — live container, digest `sha256:56da5afd…`, host Docker with `-p` port-mapping): the `0024` `/retry-exhausted` topology (`retry_policy:{retry_on:"5xx",num_retries:1}` → a single-endpoint cluster whose backend 503s every attempt) with a `{rc,rcd,rf}` `json_format` access-log, driven by `GET /retry-exhausted`, emits — byte-stable across repeated drives:
  ```
  {"rc":503,"rcd":"via_upstream","rf":"URX"}
  ```
  `%RESPONSE_FLAGS%` = **`URX`** is a single, clean, brace-free, deterministic constant (no combination). The `%RESPONSE_CODE%` is `503` (the last upstream response verbatim) and the `%RESPONSE_CODE_DETAILS%` is `via_upstream` (NOT a unique string — see the recon note above). So `URX` is byte-exact cross-proxy and witnessable; the rcd already matches (no change).
- **1:1 with the retry-limit-exceeded path, via a clean boolean discriminator.** The retry loop (`hcm.rs:980`-`1103`) sets `final_retriable` per attempt (`:1057`); at loop exit the post-loop split (`:1126`-`1131`) ticks `upstream_rq_retry_limit_exceeded` IFF `attempts > 1 && !retry_budget_blocked && final_retriable` (L9 — the budget of `num_retries` consumed with the final attempt still retriable; the L7-exclusive retry-BUDGET-blocked exit is excluded by `!retry_budget_blocked`). Setting a new `retry_limit_exceeded_for_log` boolean at THAT exact site is provably 1:1 with Envoy's `URX` (the same gate as the counter Envoy increments for `URX`), exactly as `upstream_rq_retry_limit_exceeded` is 1:1 with the L9 path.

envoy-rust on this path TODAY emits `rcd:"via_upstream"` (CORRECT — matches Envoy) + `rf:"-"` (WRONG — the phase-48/49/50 derive maps only the three rcd strings, and `via_upstream` falls to `_ => "-"`), so this phase corrects a real `%RESPONSE_FLAGS%` divergence and lights up the fourth flag, recon-confirmed, reusing a fully-built + already-green retry-exhausted trigger.

## §2 — Scope (minimum-viable, ADR-0108)
