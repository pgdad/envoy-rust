2. **The schema is a faithful, on-disk-verified match to the established `Cluster` cascade.** Cluster A confirmed all four new structs carry `#[derive(Debug, Serialize, Deserialize, PartialEq)]` + `#[serde(deny_unknown_fields)]`, NO `Clone` — byte-identical to the on-disk `Cluster` derives (lock-in #5 / SPEC-correction #1). `Serialize` is present (feeds `/config_dump` per the 08.1 cascade). `http_health_check: Option<HttpHealthCheck>` (lock-in #6) keeps `UnsupportedHealthCheckType` a genuinely-constructible variant (verified non-dead-code via a `-D warnings` build) while `deny_unknown_fields` rejects TCP/gRPC/custom checkers + the deferred upstream knobs at parse time (test `cluster_rejects_unknown_health_check_field`). `Percent { value: f64 }` is correctly distinct from the phase-11 `FractionalPercent`. 3. **The validator runs for every cluster and is panic-free on attacker-controlled config.** Cluster A confirmed `validate_health_checks(cluster)` sits at the tail of the per-cluster `for` loop in `validate()` with no `continue` short-circuit, so no malformed health-check config can slip through unvalidated (first-error convention). The dereference of the http checker is guarded behind `.ok_or_else(...)?`; the duration guard `match parse_duration(raw) { Ok(d) if !d.is_zero() => {}, _ => Err(...) }` correctly rejects BOTH `0.5s` (parse failure — `parse_duration` parses the numeric prefix as `u64`) and `0s` (zero), each test-locked to the right `field`; the half-open range check `start >= end` on `i64` and the panic-range check `(0.0..=100.0).contains(&p.value)` on `f64` are total (no overflow/panic, NaN correctly rejected); `{ value: 0 }` validates OK. No unwrap/panic on config input anywhere in the validate path — important because this surface is exercised by the `parse_bootstrap` fuzz target.

4. **The `EndpointHealth` gauge accounting is edge-guarded, idempotent, and convergent.** Cluster B traced the gauge edges: `inc()` fires only on the `state == UNHEALTHY && n >= healthy_threshold` transition; `dec()` only on the mirror `HEALTHY → UNHEALTHY` edge. The `repeated_success_while_healthy_does_not_double_increment_gauge` test directly proves no double-inc. The shared `Arc<Gauge>` starts at 0 (all endpoints Unhealthy per §6.2 item-1) and converges to exactly the healthy-endpoint count under any sequence of `record_*`. Each `inc`/`dec` is itself a single atomic RMW (`fetch_add`/`fetch_sub`), so the aggregate count is never lost regardless of ordering. The constructor is robust even at `threshold = 0` (validator-unreachable, but `n=1 >= 0` flips on the first success and the edge-guard still prevents double-inc).

5. **The `pick()` panic logic is strictly-below-correct and tested on both sides of the boundary.** `healthy_percent < self.panic_threshold` (strictly `<`, not `<=`) is locked by `pick_does_not_panic_at_exactly_the_threshold` (1-of-2 healthy = 50% vs threshold 50.0 → `50 < 50` false → no panic → only the healthy endpoint) AND `pick_panics_to_all_when_below_threshold` (0% < 50% → panic → round-robin over ALL). **M1. `crates/envoy-config/src/bootstrap.rs` `validate_health_checks` uses `< 1` on a `u32` field where `== 0` reads marginally clearer.** The two threshold guards (`hc.healthy_threshold < 1`, `hc.unhealthy_threshold < 1`) are functionally identical to `== 0` on an unsigned type. **Why it matters:** D-3.4 readability; clippy *could* flag `clippy::absurd_extreme_comparisons` under some configs. **Why it does NOT rise above Minor:** the lint did NOT fire under the `-D warnings` build (Cluster A ran it), and `< 1` matches the lock-in #7 wording ("must be `>= 1`"); functionally correct + test-locked. **Fix sketch:** `== 0` (~2 LoC) if a future phase touches this validator. **Disposition:** awareness-only style nit; **no action recommended** (not worth a churn commit). Named owner: none.

**M2. `crates/envoy-cluster/src/health.rs` `EndpointHealth` `Relaxed`-ordering correctness rests on the single-writer-per-endpoint premise (lock-in #11), which is asserted in the doc comment + lock-in but NOT enforced by the type/API — a forward dependency the 12.2 review MUST verify.** `record_success`/`record_failure` each perform a load-modify-store on `state` (load state → conditional store → gauge edge) that is race-free ONLY if a single writer ever touches a given endpoint's `EndpointHealth`. Lock-in #11 asserts the 12.2 design instantiates exactly one probe task per (cluster, endpoint), but nothing in the current `EndpointHealth` type prevents two `Arc` holders from calling `record_*` concurrently; if 12.2 ever wires a many-writers-per-endpoint topology, the read-modify-store becomes a lost-update race (e.g. two concurrent failures could each observe `HEALTHY` and both `dec()`, double-decrementing the gauge below the true healthy count). **Why it matters:** the `Relaxed` ordering is sound for 12.1 (no live writer exists; `pick()`'s read-side `is_healthy()` is a single un-tearing `AtomicU8` load) but the soundness is conditional on a premise the 12.2 implementation owns. **Why it does NOT rise above Minor for 12.1:** there is no production writer in 12.1, the seam is correctly shaped, and the premise is the recommended design (one task per endpoint) — this is a sanctioned 12.2 handoff, not a 12.1 defect. **Fix sketch:** the 12.2 review verifies the probe-task topology instantiates exactly one writer per endpoint before relying on `Relaxed`; OR (if many-writer ever becomes necessary) `record_*` is reworked to a CAS loop / `fetch_update`. Optionally, a one-line comment on `EndpointHealth` reaffirming the single-writer contract at the API boundary (folds in the Task-3 doc-precision minor). **Disposition:** awareness-only forward dependency; **close at the 12.2 review** (verify single-writer topology). Named owner: **phase 12.2 review**.

**M3. `crates/envoy-cluster/src/cluster.rs` `pick()` makes two passes over the health slice (compute `healthy_count`, then build `healthy_idx`).** A single pass collecting indices and taking `.len()` would avoid the double `filter`. **Why it matters:** micro-performance / D-3.4 conciseness. **Why it does NOT rise above Minor:** endpoint counts are tiny; the two-pass form is arguably clearer; a flip between the two reads is harmless (worst case one extra/fewer endpoint considered for a single pick, self-correcting next pick). **Fix sketch:** single-pass `enumerate().filter(...).map(|(i,_)| i).collect()` then `.len()` (~5 LoC) if a future phase touches `pick()`. **Disposition:** awareness-only micro-style; **no action recommended**. Named owner: none.

The rationale prose resolves this, but the Equivalence cell alone could mislead a reader expecting a non-zero value at 12.1. **Why it matters:** D-3.4 stranger-readability (the contract is the canonical reference). **Why it does NOT rise above Minor:** the rationale column states the 12.1=0 / 12.2-driven distinction explicitly; purely cosmetic. **Fix sketch:** `value-exact (12.2 steady state; reads 0 at 12.1)` (~1 LoC) — naturally folds in at the 12.2 task where the gauge becomes driven. **Disposition:** awareness-only doc-precision; **close opportunistically at 12.2** (where the gauge goes live and the row is naturally revisited).
