## §1 — Why this pick

`%RESPONSE_FLAGS%` already renders in all three encoders (`default_format.rs:60`, `json_format.rs:242`, `command_operator.rs:526`); phase 48 (ADR-0105) made the field per-request via the derive at `hcm.rs:1237` (consumed at the unified H1 record-build site `:1225`), and phase 49 (ADR-0106) added the second arm `UH`. `UO` is the cheapest next flag onto an already-built, already-green failure path:

- **The overflow 503 path is already implemented and already differentially green.** envoy-rust synthesizes the circuit-breaker overflow 503 via the dedicated `synth_overflow` helper (`hcm.rs:1729` — byte-exact 81-byte body `upstream connect error or disconnect/reset before headers. reset reason: overflow` + `x-envoy-overloaded: true`). Fixture `0023-upstream-circuit-breaker-max-pending-requests` (phase 15, ADR-0043) ALREADY proves that 503 wire response is byte-exact cross-proxy on the `circuit_breakers.thresholds: [{ max_connections: 1, max_pending_requests: 0 }]` trigger. No new trigger surface, no new synth path — only the access-log `rcd`/`rf` rendering is unbuilt (and currently WRONG: it renders `rcd:"via_upstream"`).
- **State-0 recon-CONFIRMED at `envoyproxy/envoy:v1.33.0`** (this session — live container, digest `sha256:56da5afd…`, host Docker with `-p` port-mapping): the `0023` topology (STATIC `backend_cluster`, `max_connections:1`/`max_pending_requests:0`, single dead endpoint `127.0.0.1:1`) with a file access-log `json_format` of `{rc, rcd, rf}`, driven by a single `GET /`, emits — byte-stable across repeated drives:
  ```
  {"rc":503,"rcd":"upstream_reset_before_response_started{overflow}","rf":"UO"}
  ```
  `%RESPONSE_FLAGS%` = **`UO`** is a single, clean, brace-free, deterministic constant. The `%RESPONSE_CODE_DETAILS%` carries a brace `{overflow}`, but the brace content is a FIXED reset-reason enum (`overflow`) — NOT the OS-derived error phrase that makes the connect-failure path non-deterministic (the connect-failure rcd is `upstream_reset_before_response_started{remote_connection_failure|delayed_connect_error:_Connection_refused}`, ADR-0102 §B). So the overflow rcd is byte-exact cross-proxy; only the connect-failure rcd is not. This recon CORRECTS the imprecise "connect-failure / overflow details are NON-DETERMINISTIC" lumping in ADR-0102 §B (which only ever recon'd the connect-failure path).
- **1:1 with the overflow path, via a clean discriminator.** The `max_pending_requests:0` trigger reaches `synth_overflow` through the pool (`PoolError::PendingOverflow`, `pool.rs:270` → `hcm.rs:510-515`), returned from `run_attempt` as `AttemptResult { endpoint: Some(endpoint), outcome: None, upstream_response: false }` (`hcm.rs:632-643`). At the retry-loop consumption site (`hcm.rs:990-1002`), `attempt.endpoint` is `Some`, so the code enters the `if let Some(endpoint)` branch and sets `via_upstream` today. Within that branch the four reachable outcomes are `Some(Response)` (success, `:600`), `Some(Reset)` (`:620`), `Some(ConnectFailure)` (`:629`), and `None` (overflow, `:640`) — so **`outcome == None` (with `endpoint: Some`) is UNIQUELY the pool-overflow result** (`outcome: None` only appears twice — `:439` is the no-healthy `endpoint: None` arm, excluded by the `Some` guard, and `:640` the overflow arm). Setting the overflow detail under that discriminator is provably 1:1 with the overflow 503, exactly as `no_healthy_upstream` (phase 45) is 1:1 with the no-healthy 503 and `route_not_found` (phase 46/47) is 1:1 with the no-route 404.

envoy-rust on this path TODAY emits `rcd:"via_upstream"` + `rf:"-"` (the loop site unconditionally writes `via_upstream`; the phase-48/49 derive maps only `route_not_found`/`no_healthy_upstream`), so this phase corrects a real divergence (the overflow path is NOT a real upstream response) and lights up the third `%RESPONSE_FLAGS%` value, recon-confirmed, reusing a fully-built + already-green 503 trigger.
