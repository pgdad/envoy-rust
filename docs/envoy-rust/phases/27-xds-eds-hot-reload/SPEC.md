## 0. Critical scoping findings (READ FIRST) — EDS is the least-invasive live mutation AFTER RDS; the watcher + atomic-swap + harness primitives already exist from phase 26

The state-1 brainstorm (read-only recon at HEAD `b01e7eb`) identified five findings that make EDS hot-reload a **single, bounded, deterministic phase** — the project's second post-construction live mutation, and the least invasive one after RDS:

1. **An EDS reload mutates ONLY a cluster's endpoint (host) set; the cluster lifecycle stays immutable, and host selection is per-request stateless.** `Cluster.endpoints: Vec<SocketAddr>` (`crates/envoy-cluster/src/cluster.rs:80`) is built once at `from_bootstrap` (`cluster.rs:741-803`, parsed from the cluster's `ClusterLoadAssignment`) and read on every request by the round-robin LB `pick()` (`cluster.rs:274`, an `AtomicUsize` cursor modulo the endpoint count). Nothing else holds per-request host state — selection is a pure function of `(endpoint set, cursor)`. So hot-reload = replace the address `Vec` the LB reads. The ONLY structural change: the owned `Vec<SocketAddr>` becomes a **shared swappable handle** that BOTH the LB (reads per request) and the watcher (writes on reload) hold. **No cluster add/remove, no pool/health-checker/outlier-sweeper/budget spawn-or-teardown, no socket churn** — the reasons CDS and LDS hot-reload remain deferred (§4). This is why EDS is the correct SECOND hot-reload target, directly after RDS.

2. **Phase 26 already built every piece of infrastructure this phase needs — the watcher primitive, the atomic-swap-handle pattern, the warm-reject reload pipeline, AND the mid-test atomic-rename harness capability.** `crates/envoy-http1/src/rds_watcher.rs` is the template (poll `path` mtime per ~1 s interval, `CancellationToken` shutdown discipline, reparse-OUTSIDE-the-lock, atomic `store`, warm-reject-keeping-last-good, per-reload counter ticks; ADR-0066 P2 confirmed an **atomic-rename** reload trigger which envoy-rust's mtime poll detects). The differential harness already rewrites a mounted dynamic-config file mid-test **via atomic-rename, then settles** on a bounded wait-for-convergence (the phase-26 D6 capability, `tests/differential/src/lib.rs`). Phase 27 therefore builds **almost no new infrastructure**: it (a) generalizes the phase-26 watcher to also watch EDS files (the M19/M20/M21 + phase-26 watcher-generalization opportunity — §6.11), (b) migrates the cluster endpoint set to a swappable handle (D1), (c) adds the EDS reparse→validate→swap pipeline (D3), and (d) adds the one genuinely-new harness capability for THIS phase: a **second distinguishable backend** (finding 4). The settle-then-probe + atomic-rename + warm-reject machinery is reused, not re-authored.

3. **The MVP boundary is PLAIN CLUSTERS ONLY (no active health-checking, no outlier detection) — the endpoint-index-aligned health/outlier machinery is the deferred hard part.** `Cluster` holds `endpoint_health: Option<Vec<Arc<EndpointHealth>>>` and `outlier_detection: Option<OutlierDetectionState>` (`cluster.rs`) — when configured, these are **arrays index-aligned with the endpoint `Vec`**, with one `envoy-health::Scheduler` probe task spawned per `(cluster, endpoint)` pair and per-endpoint ejection state. A reload that CHANGES the endpoint set (especially its size) would force **spawning probe tasks for new endpoints, draining them for removed ones, and rebuilding the index-aligned ejection arrays** — the exact per-endpoint lifecycle churn that makes CDS hot-reload heavyweight. **Phase 27 scopes EDS hot-reload to clusters WITHOUT active HC / outlier detection** (a pure address-`Vec` atomic swap the stateless LB picks up); the HC/OD-aligned-array rebuild on reload defers to a follow-up (§4). For a plain cluster the swap is genuinely side-effect-free: `endpoint_health`/`outlier_detection` are `None`, so there are no aligned arrays to rebuild. **§6.2 / the PLAN-write decide the disposition of an EDS cluster that ALSO configures HC or OD** — either reject-loud at config time (out-of-MVP-scope, the `deny_unknown_fields` philosophy) OR leave its endpoints at initial-load (no watcher) — and reserve **ADR-0068** if that decision diverges from the projection.

4. **An endpoint-set change within ONE cluster is NOT observable through a single echo backend — the phase needs a distinguishing observable, projected as TWO distinguishable single-endpoint backends + the `cluster.<name>.update_*` reload counters.** Phase 26 (RDS) observed the route change via *which cluster's* `upstream_rq_total` advanced — a per-cluster discriminator. EDS changes the endpoint list WITHIN one cluster, so the cluster name (hence the per-cluster counter) does not change, and: `cluster.<name>.membership_total` is **not emitted** (`cluster.rs:963`), `membership_healthy` is **health-check-gated** (absent on a plain cluster), and there are **no per-endpoint request counters**. So a single echo backend yields an identical 200 response regardless of which endpoint the LB picks. The phase therefore needs a distinguishing observable. **Projected (§6.2-verified): two distinguishable single-endpoint `http1-echo-server` backends** (`backend_1` and `backend_2`, distinguishable by a per-backend echo marker), with the EDS `ClusterLoadAssignment` swapped from listing `backend_1` to listing `backend_2` — the echo marker changing on live traffic without a restart is the honest "traffic re-targeted" signal — **plus** the `cluster.<name>.{update_attempt,update_success}` counters advancing (the stat signal). This is the **minimal version of the deferred LB distinguishable-backend harness** (two single-endpoint backends, NOT a general N-backend/locality/weight framework — exactly as ADR-0065 framed RDS needing "a two-distinguishable-cluster pair, not a general framework"). §6.2 confirms the exact stat taxonomy and whether a simpler **liveness-flip** (live→unreachable endpoint, 200↔503 — no second backend) is preferable.

5. **Minimum-viable EDS hot-reload adds ZERO new config schema — it is pure runtime behavior on the EXISTING `eds_cluster_config.eds_config.path_config_source.path`.** Envoy's file-based xDS is **always-watching by default** (no opt-in field); envoy-rust matches by spawning a watcher for EVERY `eds`-configured cluster. So there is no new `ConfigError`, no new parse surface, and (projected) no new fuzz seed. Phase 26 (ADR-0066 P2) already established that **atomic-rename triggers the reload without `watched_directory`** and that envoy-rust's mtime poll detects it — that finding carries to EDS unchanged, so no `watched_directory` field is projected (§6.2 re-confirms for the EDS file).

**Consequence:** phase 27 needs **NO new crate** (the EDS watcher generalizes the phase-26 watcher; the swappable endpoint handle uses `std::sync::RwLock<Arc<…>>` or `tokio::sync::watch` — both already in use, NO new `arc-swap` dep), **NO new top-level Cargo dep**, and **NO new reload/settle harness machinery** (reuses phase-26's atomic-rename mid-test rewrite + wait-for-convergence) — but it DOES need **one genuinely-new harness capability: a second distinguishable backend** (§D6). Projected surface ~900–1300 LoC — single phase (less than phase 26, since the watcher + harness reload primitives are reused), with the §6.1 split valve reserved.

These findings are ratified in **ADR-0067** (landed at this brainstorm commit).

## 1. Goal and acceptance signal

Phase 27 makes **file-based EDS endpoint assignments hot-reloadable**. When a cluster configures `eds_cluster_config.eds_config.path_config_source.path` and that file is edited (atomic-rename) while the proxy is running, both upstream Envoy and envoy-rust:

- **detect the change and re-load the named `ClusterLoadAssignment`** without a restart and without tearing down the cluster,
- **atomically apply the new endpoint set to live traffic** (subsequent requests are load-balanced over the new endpoints; in-flight requests are unaffected — they complete against the endpoint already picked),
- **expose the reload observably**: the per-cluster `cluster.<name>.{update_attempt,update_success}` counters advance past their initial-load values, and `/config_dump`'s `EndpointsConfigDump` reflects the new assignment (+ updated `last_updated`),
- **on a bad reload (malformed file / unresolvable assignment), keep serving the last-good endpoint set** and tick the failure counter (the proxy-already-serving warm-reject posture — §5.5, reusing the phase-26 §5.5 carve-out).

**Differential surface added by phase 27:**

- **Fixture `0035-xds-eds-hot-reload`** — a single cluster `eds_backend` whose endpoint set is EDS-supplied, reloaded mid-test, bilaterally asserted. Both proxies receive identical bootstraps: admin + `node` + **two distinguishable single-endpoint `http1-echo-server` backends** (`backend_1`/`backend_2`, distinguishable per §6.2 — a per-backend echo marker) + one EDS cluster `eds_backend` (`type: EDS`, `eds_cluster_config.eds_config.path_config_source.path: <EDS_PATH>`, **no active HC / no outlier detection** per §0 finding 3) + one static HTTP/1.1 listener routing `/probe` → `eds_backend`. The test runs in **three phases against the running proxies**:
  1. **Pre-reload (initial load):** `GET /probe` → **200**, served by `backend_1` (the initial EDS file assigns `eds_backend` → `[backend_1]`); assert the echo marker identifies `backend_1`; assert `cluster.eds_backend.{update_attempt,update_success}` at their initial-load values (§6.2-verified, projected `1/1`).
  2. **Reload:** the harness **rewrites the mounted EDS file via atomic-rename** (the phase-26 D6 capability, reused) so `eds_backend` → `[backend_2]`, then **settles** (the phase-26 wait-for-convergence pattern, bounded poll on a discriminating observable — the echo marker OR the `update_success` counter advancing).
  3. **Post-reload:** `GET /probe` → **200**, now served by `backend_2` (the discriminating observable: the routed-to endpoint CHANGED without a restart); assert `cluster.eds_backend.{update_attempt,update_success}` ADVANCED (projected `2/2`); assert `/config_dump` `EndpointsConfigDump` now reflects the `backend_2` assignment. Plus a **bad-reload probe** (rewrite the EDS file to malformed content → settle → `GET /probe` still served by `backend_2` [last-good set kept] + the failure counter ticked — §6.2 item 5 fixes the exact counter).

  The discriminating differential observable is the **endpoint set re-targeting live traffic without a restart** + the **reload counters advancing** — a proxy that ignored the file edit would keep serving `backend_1` and leave the counters at their initial-load values. Probe shape, exact stat names/values on reload, the bad-reload disposition, and the config_dump shape are §6.2-verified (§6.2 items 1–6).

**Acceptance signal (a)–(f), per `BOOTSTRAP_PROMPT.md` §7.5:**

- **(a)** Fixture `0035-xds-eds-hot-reload` green at Docker-gated **Linux CI** (the AUTHORITATIVE anchor per ADR-0049 / ADR-0066 — the reload trigger is unobservable on macOS Docker / Docker-Desktop virtiofs; §0 finding 2, §5.7).
- **(b)** All **34 pre-existing differential fixtures** (`0001` through `0034`) **remain green simultaneously** at the same CI run (regression-equivalence per §7.5 (b)). The EDS watcher is inert when no cluster configures `eds`; for the ONE existing EDS fixture (`0029-xds-file-based-eds`), the envoy-rust side now spawns an **idle endpoint-watcher** (the file is never edited mid-test) — its `cluster.*.update_*` counters stay at their initial-load values and its data plane is unchanged, so `0029` stays green (the critical regression-sensitivity witness — §5.2). The endpoint-handle migration (`Vec` → swappable handle) is behavior-preserving for every non-reloading request and for every existing cluster fixture (`0020`–`0029` exercise the LB / pools / health / outlier paths that read the endpoint set).
- **(c)** `h2spec` continues at ≥95% (parent-05 baseline). Phase 27 does not touch HTTP framing.
- **(d)** `parse_bootstrap` fuzz target clean for the short-budget CI run (projected NO new seed — no new parse surface per §0 finding 5).
- **(e)** `cargo build --workspace --all-targets`, `cargo clippy --workspace --all-targets --all-features -- -D warnings` (run PER TASK in the state-3 arc, per `project_state3_arc_skips_clippy`), `cargo fmt --all -- --check`, `cargo test --workspace`, `cargo deny check` all clean — plus the standalone-crate builds (`-p envoy-cluster -p envoy-config` + the watcher's owning crate) per `project_isolated_crate_build_blindspot`.
- **(f)** `REVIEW.md` approved.

A **single CI run** must light up gates (a) through (e) **simultaneously** (continues the project precedent).

## 3. Deliverables

Phase 27's scope is enumerated as deliverables `D1`–`D8` below. **The state-2 PLAN-writer organizes deliverables into tasks AND evaluates the §6.1 split gate.** Deliverables are LISTED roughly in execution order; the SPEC constrains the surface, not the task organization.

### D1 — Endpoint-set-handle migration (`Vec<SocketAddr>` → a shared swappable handle)

`Cluster.endpoints: Vec<SocketAddr>` (`crates/envoy-cluster/src/cluster.rs:80`) becomes a **shared, atomically-swappable handle** — projected `Arc<RwLock<Arc<Vec<SocketAddr>>>>` or `tokio::sync::watch` (NO new `arc-swap` dep per §5.1; the exact type is a PLAN-write decision weighing per-request read cost — the LB `pick()` reads the endpoint set on EVERY request — against §5.1, reusing the phase-26 D1 decision verbatim). The per-request consumer (`pick()` at `cluster.rs:274`, the round-robin cursor; the health-/outlier-slow-path filters that also index the endpoint set) loads the current `Arc<Vec<…>>` at request entry (a cheap pointer clone) and uses it for the whole selection — guaranteeing **in-flight isolation** (§5.4). The construction site (`cluster.rs:741-803`) seeds the handle; the watcher (D2) holds the write end. **CARRY-FORWARD WARNING for the state-3 executor:** this is a workspace-compile-affecting field-type change touching every `self.endpoints`/`cluster.endpoints` read site across `envoy-cluster` (the LB cursor, the health/outlier slow paths, the membership accounting, the config_dump renderer, and the AtomicUsize-cursor-vs-endpoint-count interaction — a shrinking endpoint set must not let the cursor index out of bounds); the PLAN-write's SPEC-correction pass enumerates the exact sites (the phase-26 `route_config`→swappable-handle migration is the precedent for the sweep discipline, and the M26-1 "read the set ONCE per request" lesson applies — §6.11).

### D2 — The EDS file watcher (generalize the phase-26 watcher, OR a sibling `EdsWatcher`)

The phase-26 `RdsWatcher` (`crates/envoy-http1/src/rds_watcher.rs`) is **generalized** to a watcher that polls each watched file's mtime and, on an atomic-rename-detected change, invokes a reload action (D3) — OR a sibling `EdsWatcher` is added (PLAN-write call, weighing the §6.11 generalization pressure: there are now TWO file watchers, so a parameterized `XdsFileWatcher<reload-fn>` is the natural factoring, but it must not over-abstract). The watcher likely **moves to a shared location** (e.g. `envoy-config` or a small dedicated module) since EDS concerns CLUSTERS (`envoy-cluster`), not the HCM (`envoy-http1`) where `RdsWatcher` currently lives — this crate-placement question is a PLAN-write decision. Each watched EDS target = `(path, cluster_name, write-handle-to-the-cluster's-endpoint-set, the cluster.<name>.* stat handles)`. The loop polls `path` mtime per interval (the reused ~1 s default; NOT a config field per §0 finding 5); on change → invoke D3. `envoy-bin` (`crates/envoy-bin/src/main.rs`, beside the phase-26 `RdsWatcher` spawn) constructs it once after building the clusters, passing the shared `CancellationToken`. Inert when no cluster uses `eds` (no targets → no loop).

### D3 — The reload pipeline (re-parse → re-validate → atomic swap; stat-tick)

On a detected change for a target: re-read the file → re-parse via the existing `eds.rs` ClusterLoadAssignment parser (phase 21, reused verbatim) → select the `ClusterLoadAssignment` by `cluster_name` → re-validate (parseable endpoint addresses; the non-empty-endpoints gate per the phase-21 validator; §6.2 item 5 confirms whether an empty assignment is warm-rejected or applied) → on success: build a new `Arc<Vec<SocketAddr>>` and **atomically store it into the write-handle** (D1); tick `update_attempt`+`update_success`; update the config_dump `last_updated` (D5). On failure (file unreadable / parse error / `cluster_name`'s assignment absent / unparseable endpoint / empty per §6.2): **KEEP the last-good endpoint set unchanged**; tick `update_attempt`+`update_failure` (parse/IO) or `update_rejected`/`update_empty` (semantic) per the §6.2-item-5 split. **This reuses the phase-26 §5.5 warm-reject carve-out** (the proxy is already serving; ADR-0049's all-fatal posture governs STARTUP, not reload). **§6.2 verifies the EDS analog of the phase-26 unknown-cluster divergence (ADR-0066 P5(iii))** — e.g. whether Envoy applies an empty/zero-endpoint EDS update (cluster → 0 hosts → 503) while envoy-rust warm-rejects it to avoid an empty-LB panic; if so, that is a recorded deliberate divergence (reserve ADR-0068).

### D4 — Per-cluster `cluster.<name>.update_*` counters tick per reload (reuse phase-21 registration)

The phase-21 conditional registration (`cluster.<name>.update_attempt/update_success/update_failure/update_rejected/update_empty` registered when the cluster is `eds`-typed; `cluster.rs:974-977,1097`) is UNCHANGED; phase 27 wires the **increment sites in the reload pipeline (D3)** rather than only at initial load. The stat handles must be threaded from the cluster construction site to the watcher target (D2) — projected: the watcher target carries `Arc<Counter>` clones, the established 06.x `Arc<Counter>`-shared-handle idiom. (Initial-load increments stay where phase 21 put them; the watcher adds the per-reload increments.)

### D5 — `/config_dump` `EndpointsConfigDump` `last_updated`/assignment update on reload

The phase-21 `EndpointsConfigDump` entry (`crates/envoy-admin/src/endpoint.rs`) reads the CURRENT endpoint assignment; with D1 making it swappable, the admin renderer must read through the swappable handle (not a startup snapshot) so a post-reload `/config_dump` reflects the new assignment. The `last_updated` field updates on each successful apply (§6.2 item 6 fixes the exact shape — projected analogous to ADR-0066 P6: `last_updated` changes, the embedded assignment reflects the new endpoints, no `version_info` for file-based EDS). Emitted ONLY when some cluster uses `eds` (the phase-21 conditionality; the other config_dump sections untouched).

### D6 — Harness: the second distinguishable backend (the one genuinely-new harness capability)

`tests/differential/` gains the ability to **spawn a second distinguishable single-endpoint backend** so the EDS endpoint re-targeting is observable on the wire (§0 finding 4): `backend_1` and `backend_2`, each a real `http1-echo-server`, distinguishable by a per-backend echo marker (§6.2 item 3 fixes the exact discriminator — a response header, a body marker, or the `cluster.<name>` it is reached through). This is the minimal version of the deferred LB distinguishable-backend harness (two single-endpoint backends, NOT a general framework). The **mid-test atomic-rename file-rewrite + settle-then-probe capability is REUSED from phase-26 D6** (not re-authored); the expectations schema's "reload step" + post-reload probe/assertion block (phase-26) is reused, extended to carry the per-backend discriminator assertion. ## 4. Out of scope (deferred non-goals)

Each schema-bearing deferred item below is rejected by `#[serde(deny_unknown_fields)]` today (a bootstrap configuring it fails parse loudly — nothing is silently under-implemented):

- **Hot-reload of CDS / LDS** — the harder live mutations: CDS cluster add/remove (spawn/teardown of pools + health checkers + outlier sweepers + budget primitives + the swappable `ClusterManager` handle), LDS listener add/remove (socket bind/unbind + connection drain + in-place listener update). Each is a future hot-reload phase building on THIS phase's + phase 26's watcher primitive + atomic-swap pattern. EDS is chosen first among the three because its live mutation is a stateless endpoint-`Vec` pointer swap (§0 finding 1).
- **EDS hot-reload for clusters WITH active health-checking or outlier detection configured** — the endpoint-index-aligned `endpoint_health`/`outlier_detection` arrays + the per-`(cluster,endpoint)` `envoy-health::Scheduler` probe tasks would need spawn/drain/rebuild on a count-changing reload (§0 finding 3) — the same per-endpoint lifecycle churn that defers CDS. MVP scopes to plain clusters; this aligned-array rebuild is the natural next EDS-hot-reload increment. The §6.2/PLAN-write disposition of an EDS+HC/OD cluster (reject-loud vs no-watcher) is recorded; ADR-0068 reserved if it diverges.
- **`LbEndpoint` weight / health-status / priority / locality semantics changing under reload** — the MVP swaps the endpoint ADDRESS set only (the round-robin LB over the address `Vec`). `load_balancing_weight`, `health_status`, locality-weighted LB, and priority-failover endpoint fields are not exercised by the reload (they layer onto the LB-policy family). Deferred.
- **inotify/`watched_directory` mechanism exactness** — envoy-rust polls mtime (behavior-equivalent post-settle; ADR-0066 P2 established atomic-rename triggers it without `watched_directory`). Matching Envoy's exact inotify event semantics is out of scope.
- **Cluster warming on EDS update** — Envoy warms an endpoint set before activating; an MVP plain-cluster address swap needs no warming (the cluster pre-exists, the pool is keyed by `(cluster, endpoint)` and naturally orphans/creates entries). The new-resource-warming machinery defers with CDS hot-reload.
- **A configurable poll interval / file-watch tuning knobs**, **`scoped_routes` / SRDS / VHDS hot-reload**, **SDS / RTDS** (any transport), the **gRPC/ADS xDS transport** (`api_config_source`/`ads_config`; the ADS state machine; the **ADR-0014 protos supersession**), **delta xDS**, **`initial_fetch_timeout`**, **REST xDS** — all carried unchanged from the phase-18→26 ledger.

## 5. Architectural invariants

### 5.1 No new crate, no new top-level Cargo dep

The watcher generalizes the phase-26 poll-based watcher (`std::fs::metadata().modified()` mtime — no `notify`/inotify/kqueue dep). The swappable endpoint handle uses `std::sync::RwLock<Arc<…>>` or `tokio::sync::watch` (both already in use from phase 26) — NOT a new `arc-swap` dep. The reload pipeline reuses the existing `eds.rs` parser + the phase-21 validator. (If the PLAN-write finds a no-new-dep swap handle materially worse for the per-request LB read hot-path, an `arc-swap` dep is the documented fallback — but the default is dep-free, as decided for phase 26.)

### 5.2 Inert-when-unconfigured + the 0029 idle-watcher regression witness

No cluster with `eds` → no watcher spawned, zero behavior change. For the ONE existing EDS fixture `0029-xds-file-based-eds`: the envoy-rust side now spawns a watcher, but the file is never edited mid-test → the watcher idles, the `cluster.*.update_*` counters stay at their initial-load values, and the data plane is byte-identical. **0029 staying green is the load-bearing regression witness** — it proves the endpoint-handle migration (D1) is behavior-preserving and the idle watcher is side-effect-free. All 34 existing fixtures (notably `0020`–`0029`, which read the endpoint set via the LB / pools / health / outlier paths) stay green simultaneously.

### 5.3 The cluster lifecycle stays immutable; only the endpoint address set mutates

Phase 27 mutates ONLY a plain (no-HC/no-OD) cluster's endpoint address set. The `ClusterManager` membership, listeners, connection pools (keyed by `(cluster, endpoint)` — naturally orphan/create on an address-set change), and budgets stay immutable post-construction (the ADR-0048 §5.3 invariant holds for everything except the EDS endpoint set). A reloaded assignment may list any parseable endpoint address; it may NOT introduce HC/OD machinery (those clusters are out of MVP scope — §0 finding 3) and an empty/unresolvable assignment → the reload is warm-rejected, last-good kept (§5.5, §6.2 item 5).

### 5.4 In-flight request isolation (atomic swap, read-once-per-selection)

Each request loads the current endpoint-set `Arc` ONCE at LB selection and uses that snapshot for the request's upstream lifetime. A reload that lands after selection does not affect the in-flight request (it already holds its endpoint); the next request's LB pick sees the new set. The swap is a single atomic store — no torn reads, no partial endpoint sets, and the round-robin cursor must be reconciled against a possibly-shorter new set (modulo the new length — D1's cursor-bounds safety).

### 5.5 Reload is warm-reject, NOT all-fatal (reuse the phase-26 ADR-0049 carve-out)

ADR-0049's all-fatal-config posture governs STARTUP. At reload the proxy is already serving traffic; a malformed / unresolvable / (per §6.2) empty reloaded EDS file leaves the live endpoint set unchanged and ticks the failure counter — it does NOT crash the proxy. This reuses the phase-26 §5.5 warm-reject carve-out verbatim. **§6.2 verifies the EDS analog of the ADR-0066 P5(iii) unknown-cluster divergence** (whether Envoy applies an empty assignment → 503 while envoy-rust warm-rejects to avoid an empty-LB panic); a recorded deliberate divergence if so.

### 5.6 Poll-based watch; settle-then-probe determinism

The watcher polls on a fixed interval; the reload is interval-bounded, not instantaneous. The fixture asserts post-settle state via bounded wait-for-convergence on a discriminating observable (the phase-26 pattern, reused), never a fixed sleep and never a mid-reload race. In-process, `tokio::time` makes the interval controllable for a deterministic backstop.

### 5.7 Linux-CI-authoritative differential evidence (ADR-0049 / ADR-0066 Provenance)

The reload trigger (a file change observed inside the Envoy container) is unobservable on macOS Docker Desktop AND under Docker Desktop on Linux (virtiofs bind-mounts deliver no inotify — the ADR-0066 reinforcement). Fixture 0035's differential evidence is therefore authoritative only on a **native-Linux CI runner** (real bind-mount inotify; the phase-21/26 watching-class precedent). Local verification = the in-process backstop + the §6.2 wire-shape probes; the AUTHORITATIVE anchor is the native-Linux CI run.

## 8. Summary

Phase 27 lands the **first of the ADR-0065-deferred CDS/LDS/EDS hot-reload layers — file-based EDS endpoint hot-reload — chosen as the least invasive of the three**. A running cluster whose endpoint set is EDS-supplied picks up an edited EDS file (atomic-rename) without a restart: the new `ClusterLoadAssignment` is loaded, validated, and atomically swapped onto live traffic, with the per-cluster `cluster.<name>.update_*` counters advancing past their initial-load values and `/config_dump` reflecting the new assignment. It is the **second post-construction live mutation in the project**, and it **reuses phase-26's entire infrastructure** — the periodic poll-watch primitive, the atomic-swap-handle pattern, the warm-reject reload pipeline, and the mid-test atomic-rename + settle-then-probe harness capability — so it needs no new crate, no new dependency, and no new reload/settle harness machinery, only an endpoint-handle migration, the EDS reparse/validate/swap pipeline, and **one genuinely-new harness capability: a second distinguishable backend** (because an endpoint swap within one cluster — unlike RDS's per-cluster discriminator — is invisible through a single echo backend). Two deliberate scoping calls keep it minimum-viable: the MVP covers **plain clusters only (no active HC / no outlier detection)** — the endpoint-index-aligned health/outlier array rebuild is the same per-endpoint lifecycle churn that defers CDS, so it defers too — and the observability is solved with a **two-single-endpoint-backend pair** (the minimal seed of the still-deferred LB distinguishable-backend harness). The heavier live mutations (CDS cluster lifecycle, LDS socket drain) layer onto this phase's + phase 26's watcher + atomic-swap primitive in cleanly-deferred follow-ups. Because the reload trigger is unobservable under virtiofs, fixture `0035-xds-eds-hot-reload`'s differential evidence is native-Linux-CI-authoritative (ADR-0049 / ADR-0066), complemented by a deterministic in-process backstop driving the negative paths.
