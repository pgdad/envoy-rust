## §1 — Why this pick

Phase 42 (ADR-0099) added `%RESPONSE_CODE_DETAILS%` (`AccessLogRecord.response_code_details: Option<String>`) and witnessed only the two SUCCESS-path values: a `direct_response` route → `"direct_response"` (fixture 0050) and a proxy-success → `"via_upstream"` (set at the H1 proxy-success arm `hcm.rs:995`). **All FAILURE paths leave `response_code_details_for_log = None`** — the no-healthy synth-503 (`hcm.rs:431-438`), the connect-failure synth-502 (`:528`), the overflow synth-503 (`:506-513`) — so envoy-rust renders `-` (text) / `null` (json) for `%RESPONSE_CODE_DETAILS%` on every failure, while Envoy emits a specific string. M42-1 (the failure-path vocabulary, ADVANCED but NOT closed by phase 43) is the strongest owed access-log gap.

**`no_healthy_upstream` is the cheapest-STRONG failure-path detail to witness** — the state-1 recon (live `envoyproxy/envoy:v1.33.0`) confirmed:
- the no-healthy 503 emits `%RESPONSE_CODE_DETAILS% = "no_healthy_upstream"` — a **CLEAN, BRACE-FREE, DETERMINISTIC** constant (`{"rc":503,"rcd":"no_healthy_upstream","rf":"UH"}`);
- by CONTRAST the connect-failure path emits `upstream_reset_before_response_started{remote_connection_failure|delayed_connect_error:_Connection_refused}` — a **NON-DETERMINISTIC** brace sub-detail carrying an OS-derived error phrase, a POOR witness (rejected for this phase); and the overflow path likewise carries variable content.

envoy-rust's H1 no-healthy arm ALREADY returns a byte-matching 503 + `no healthy upstream` body (`synth_no_healthy_upstream`, `hcm.rs:1671`), and the access-log record is built unconditionally below the writer-arm match (`hcm.rs:1242`), so the fixture is observable. The ONLY gap is the unset detail string.
