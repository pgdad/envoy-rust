> **State-0 recon (this session) — CONFIRMS the exact gap, live Docker.** Live `envoyproxy/envoy:v1.33.0` (a sibling backend container on a dedicated Docker network, per the `state0-recon-backend-sibling-container` convention — the retry-exhausted trigger needs Envoy to actually CONNECT and receive real 503 responses, not merely fail a pick/pool gate — plus host Docker `-p` port-mapping for the Envoy container itself, ports 13000/13099), an H2C listener (`codec_type: HTTP2`, `http2_protocol_options: {}`) routing (via a plain `STRICT_DNS` H1-upstream `backend` cluster — NO `typed_extension_protocol_options` needed; the retry loop is protocol-agnostic on the upstream side, confirmed by the existing in-process test `h2_retry_limit_exceeded_path_always_503` already driving an H1-protocol backend through the H2 downstream path) to a backend that always returns 503, with `retry_policy:{retry_on:"5xx", num_retries:1}` on the route, plus a `{rc,rcd,rf,proto}` `json_format` access log, driven via `curl --http2-prior-knowledge`.

> - **Code-read finding (this session) — envoy-rust's H2 retry-loop mechanics are ALREADY correct and ALREADY tested.** The H2 retry loop (`hcm.rs:656`-`825`) is a byte-for-byte structural mirror of the H1 retry loop (phase 16's H2 Task 5): `final_retriable`/`attempts`/`retry_budget_blocked` all exist identically, and the post-loop split at `hcm.rs:815`-`821` already ticks `cluster.upstream_rq_retry_limit_exceeded()` on the SAME L9 gate H1 uses. An existing in-process test, `h2_retry_limit_exceeded_path_always_503` (`hcm.rs:4428`, landed at phase 16), ALREADY proves this gate fires correctly (status 503, `x-envoy-attempt-count: 2`, `upstream_rq_retry`=1/`_success`=0/`_limit_exceeded`=1, `upstream_rq_total`=2, `upstream_rq_5xx`=1) using `spawn_fail_then_ok_h1_upstream(503, 1000)` — an always-503 H1 backend. **This phase needs NO status-code fix and NO retry-mechanics fix** — it is a PURE access-log rcd/rf gap, exactly like phase 58's `UO` (unlike phases 50/57's H2 `UO`/`UH`, which needed genuine status-code corrections). Only the `%RESPONSE_FLAGS%` rendering is unbuilt (today it falls to the derive's `_ => "-"` arm, since the completing response's rcd is the shared `via_upstream`, not a unique string).
> - **The one genuinely new mechanism this phase introduces (mirroring H1 phase-51's own finding): `URX` is NOT rcd-derivable.** Unlike `NR`/`UH`/`UO` (each keyed off a unique `response_code_details_for_log_h2` string), the retry-exhausted path's rcd is `via_upstream` — the SAME string a normal successful upstream response carries. An rcd-keyed derive arm would mis-flag every 2xx as `URX`. `URX` requires a separate boolean discriminator threaded from the retry-loop's post-loop split, exactly as H1 needed at phase 51 — the first H2 `%RESPONSE_FLAGS%` value not 1:1 with a unique rcd.
> - **Threading finding (new relative to phase 58): `finalize_h2_stream` needs a new parameter.** Phase 58's `response_code_details_for_log_h2` was already threaded through `finalize_h2_stream` (added at phase 42); this phase's NEW boolean is not yet threaded anywhere, so — unlike phases 57/58, which only edited existing plumbing — this phase adds ONE new parameter to `finalize_h2_stream`'s signature and its SOLE call site (`hcm.rs:852`-`867`). Low risk: exactly one call site (confirmed via grep), mirroring the H1 precedent where the equivalent boolean is a simple local read post-loop, not threaded through a function boundary (H1's `finalize_h1_stream`-equivalent access-log build happens inline in the same function as the retry loop, whereas H2's is factored into a separate function — the one structural difference from H1 this phase's PLAN must handle carefully).

## §1 — Why this pick

The candidate menu (`STATE.md`, left by the phase-58 close-out) weighed: **M56-1**'s remaining H2 `%RESPONSE_FLAGS%` values (`URX`/`UF`/`UC`, now with `UH`/`UO` also consumed by phases 57/58); **M57-1** (a trivial cosmetic `content-length` header fix, not a pick driver alone — this phase does not touch `synth_h2_no_healthy_upstream()`); the phase-58 carry-forward candidate (the H2 request-budget arm's own differential fixture — smaller than a full phase, better folded into a future phase that touches that arm for an unrelated reason, mirroring how H1's M50-C waited until phase 55); the `DC` flag (rejected eight consecutive times, ADR-0102 through ADR-0115, still timing-dependent); M53-2's BEHAVIOR_CONTRACT "(H1)" qualifier (a trivial doc-only fix); and heavier family pivots (gRPC ALS/OTLP/tracing, CDS/LDS hot-reload, non-deterministic LB policies). `URX` is the cheapest-strong-differential leaf this session:

- **It is the DIRECT sequel to phase 58's `UO` witness**, exactly mirroring the H1 cadence phases 49→50→51→52→53 (`URX` is H1's FOURTH flag, phase 51) applied to the H2 cadence 56→57→58→61 (`NR`→`UH`→`UO`→`URX`). (Phase numbers 59/60 are claimed by unrelated sibling H1-perf-work sessions — disjoint surface, not renumbered here.)
- **The underlying retry-limit-exceeded mechanics are ALREADY implemented, ALREADY correct, and ALREADY covered by an in-process test** (`h2_retry_limit_exceeded_path_always_503`, phase 16) — this is the LOWEST-risk H2 flag witness in the M56-1 sequence so far: no status-code fix, no new retry logic, no new backend-driving test infrastructure (the existing `spawn_fail_then_ok_h1_upstream` helper already drives the exact always-503 topology this phase's own backstop needs).
- **State-0 recon found the gap is a clean access-log-only fix.** Live Envoy's `rcd`/`rf` pair (`via_upstream`/`URX`) is byte-stable across repeats and a full container restart; envoy-rust's H1-precedent boolean-discriminator pattern (phase 51) transcribes directly onto the H2 caller loop, with the one adaptation of threading the new boolean through `finalize_h2_stream`'s single call site.
- **The `DC` flag remains genuinely harder** (timing-dependent, eight consecutive rejections) — nothing this session changes that assessment.
