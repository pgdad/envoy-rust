## §2. Strengths

1. **The TOCTOU fix in `drain_signal()` is correct, well-documented, and regression-guarded.** `crates/envoy-listener/src/drain.rs:230-249` constructs the `Notified` future BEFORE the `state.load(Ordering::Acquire)` so the notify_waiters-counter snapshot anchors before any concurrent `drain()` can bump it. Per tokio's `Notify::notified()` docs: *"The `Notified` future is guaranteed to receive wakeups from `notify_waiters()` as soon as it has been created."* The 13-line comment block (lines 231-241) is a model of why-not-just-what documentation — it names the race shape (the pre-fix construct-then-load would snapshot post-bump and fall through to register a waiter that never unparks because sticky-drain idempotency means no second `notify_waiters()` ever fires), the source-stability anchor (tokio docs cited), and the consequence (Task 6's accept-loop `tokio::select!` re-constructs `drain_signal()` on every iteration concurrent with the admin thread that fires `drain()` — the structurally worst-case exposure point). The dedicated regression test `drain_signal_is_race_free_with_concurrent_drain` at `drain.rs:400-432` would deterministically hang under the pre-fix shape (spawned task constructs the signal future BEFORE the 2-party Barrier rendezvous; main task fires `drain()` AFTER the rendezvous). This is the project's most-Critical fix to date, landed within hours of the code-quality reviewer flagging it, with both substantive and regression coverage in the same fixup commit.

2. **The two-sequenced-CAS `drain()` semantics fire `notify_waiters` exactly once on the first valid Live→Draining or HealthcheckFailing→Draining transition.** `drain.rs:183-218` runs `compare_exchange(Live → Draining)` first; if that fails, runs `compare_exchange(HealthcheckFailing → Draining)`; the `if from_live.is_ok() || from_hc.is_ok()` gate at line 206 ensures `notify_waiters()` fires exactly once. Subsequent `drain()` calls fall through both CAS failures silently (an already-`Draining` current value matches neither expected arg). Gauges (`server.live` + `server.state`) are written BEFORE `notify_waiters` (lines 210-216 + comment) so a just-woken observer that reads the registry sees post-drain values — load-bearing ordering for the wire-level fixture-0015 assertion at `/server_info.state` post-drain. The two-CAS shape avoids the alternative of a `swap` or `store` (which would lose the "first valid transition" semantic and could double-notify). Test `drain_from_healthcheck_failing_notifies_waiters_once` at `drain.rs:434-458` exercises the second-CAS branch end-to-end.

3. **Memory-ordering discipline is consistent and pair-correct across the module.** `drain.rs` uses `Ordering::AcqRel` on every `compare_exchange` (lines 142, 165, 190, 197), `Ordering::Acquire` on CAS-failure loads (mirror arg) AND on the `current()` reader load (line 132) AND on the `drain_signal()` post-Notified state load (line 243). The release pairs with the acquire across every reader/writer boundary; observers reading the gauge registry post-drain are guaranteed to see the discriminant's post-store value. No mixed `Relaxed` or `SeqCst` choices that could break the gauge-before-notify ordering invariant. The `#[repr(u8)]` discriminant attribute at `DrainStage` makes the discriminant load-bearing for both the AtomicU8 round-trip (via `as u8` / `from_u8`) AND the `server.state` gauge value (via `stage as i64`); the lock-bearing nature is explicitly noted in the doc-comment at lines 45-49.

4. **`Listener::serve`'s drain arm and RAII-guard ordering are precisely correct.** `crates/envoy-listener/src/lib.rs:240-280` widens `serve` from 1-arg `(shutdown)` to 2-arg `(shutdown, drain: Arc<DrainState>)` and adds the new `_ = drain.drain_signal() => { drop(listener); break; }` arm at lines 277-280, positioned between the shutdown arm (lines 265-269) and the accept arm (lines 281+). Either signal triggers the same drain code path (drop the listener, break the loop, fall through to the post-loop drain-wait + `DRAIN_BUDGET` timeout block). The new RAII guard `ListenerManagerActiveGuard(Arc<envoy_stats::Gauge>)` at `lib.rs:116-128` is module-scope private (Rust forbids nested `impl Drop` inside an outer `impl`) and constructed FIRST inside `serve` at line 246 (`let _lm_guard = ListenerManagerActiveGuard::new(...)`) so its `Drop` fires LAST per Rust's reverse-declaration drop order — that places the gauge `dec()` AFTER the post-loop drain-wait completes (stragglers join or are aborted). Mirrors the 06.3 `cx_active` per-connection `ConnGaugeGuard` pattern but at the per-listener granularity. Test `serve_returns_when_drain_signal_fires` at `lib.rs:~1010-1037` asserts both `serve` completion within `DRAIN_BUDGET + 500ms` AND the post-serve gauge reads 0 (with `.expect()` not `if let Some`, hardening the test against a silently-missing gauge per Task 6 deviation #1).

5. **`/server_info` vs `/ready` asymmetry under HealthcheckFailing is correctly implemented per SPEC §5.3.** `crates/envoy-admin/src/endpoint.rs:417-420` maps `Live | HealthcheckFailing → "LIVE"` for `/server_info.state` (server-state INDEPENDENT of healthcheck — matches Envoy semantic); `endpoint.rs:330-345` maps `HealthcheckFailing → 503 "Service Unavailable\n"` for `/ready` (operator-facing: flips 503 so LB takes the instance out of rotation). The asymmetry is intentional and load-bearing — a healthcheck failure must take the instance out of LB rotation AND keep `/server_info` reporting LIVE so operators can inspect the server's actual state. Tests `server_info_state_is_live_when_drain_state_is_healthcheck_failing` + `ready_returns_503_service_unavailable_when_drain_state_is_healthcheck_failing` at `endpoint.rs:1419-1466` discriminate both surfaces.
