## §3. Issues

### Critical (must fix before phase commit)

None.

### Important (close in 06.1 or carry forward with named owner phase)

**I1. The admin handler has no idle read timeout.** `crates/envoy-admin/src/handler.rs:44-67` `read_request` loops on `stream.read(&mut scratch[..take]).await` until either `MAX_REQUEST_HEAD` is exceeded, `find_crlf_crlf` succeeds, or the peer closes (n == 0). A connected-but-silent client holds the connection open indefinitely, blocked on the kernel's read; the connection task in `JoinSet` stays parked. Compare the data-plane HCM at `crates/envoy-http1/src/hcm.rs:24` which sets `IDLE_READ_TIMEOUT: Duration = Duration::from_secs(5)` and wraps each per-request read in `tokio::time::timeout(IDLE_READ_TIMEOUT, ...)`. The admin handler intentionally does *not* implement keep-alive (each request closes the connection), but the absence of a per-read idle timeout means a single attacker connection can hold a JoinSet slot until shutdown, and N attacker connections N-multiply that hold. The shutdown path's `DRAIN_BUDGET = 5s` (`handler.rs:22`) bounds the worst-case shutdown delay, but the steady-state hold is unbounded. **Fix sketch:** wrap the `stream.read(...)` call in `tokio::time::timeout(Duration::from_secs(5), ...)` and map the `Elapsed` to a 408 Request Timeout (or just close — both proxies' admin scrape clients should retry on close). Mechanical, scoped to one site, ~10 LoC.

**Disposition:** carry forward to 06.2 or 06.3. The slow-loris exposure is a real defense-in-depth gap on the admin listener; closing in 06.2/06.3 is appropriate (admin listener is meant to be localhost-only per `Admin.access_log_path` discussion in §4 of SPEC, but envoy-rust binds wherever the config says — defense-in-depth is owed). Both reviewer and planner-of-06.2/06.3 should flag this in the carryforward inventory.

**I2. `serialize_response` injects 5 standard headers unconditionally even when the rendered response could already carry them.** `crates/envoy-admin/src/handler.rs:96-120` walks `resp.headers` writing them out, then *unconditionally* writes `cache-control: no-cache, max-age=0`, `x-content-type-options: nosniff`, `server: envoy-rust`, `date: <RFC 7231>`, `connection: close`. The current 06.1 endpoints (`render_ready`, `render_stats`, `render_stats_prometheus`, `render_404`, `render_405`) only set `content-type` / `content-length` / `allow` (where applicable) — so today the assumption holds and there are no duplicates. But the abstraction is fragile: a future endpoint that sets `cache-control: max-age=300` (e.g., a `/server_info` endpoint that's safe to cache briefly) would emit *both* headers on the wire, with the SPEC §3 D3 "non-negotiable" overriding by being last. HTTP/1.1 allows duplicate header names; the resulting wire shape is technically valid but the policy is muddled. **Fix sketch:** either (a) move the 5 standard headers into each `render_*` function (DRY-violating but explicit at the seam) or (b) in `serialize_response`, dedupe by case-insensitive header name before writing the standard headers — write only the ones not already present in `resp.headers`. Option (b) is ~10 LoC and preserves the centralized policy. **The current behavior is not a bug** for the 06.1 endpoint set; it's a latent maintenance hazard that will surface in phase 08 when the full admin endpoint surface lands.

**Disposition:** carry forward to phase 08 (full admin endpoint surface). The latent hazard surfaces precisely there. Document in the 06.1 carryforward inventory.

### Minor (awareness-only / track forward)

**M1. `serialize_response` panics implicit-okay on `resp.reason.unwrap_or("OK")`.** `handler.rs:98` uses `unwrap_or("OK")` — if a future endpoint constructs a `Response { status: 404, reason: None, ... }`, the wire output is `HTTP/1.1 404 OK\r\n` which is wrong. All current 06.1 endpoints set `reason: Some(...)`, so the path is unreachable today. **Fix sketch:** map the `unwrap_or` to the standard reason for the status code (`200 → "OK"`, `404 → "Not Found"`, `405 → "Method Not Allowed"`, `400 → "Bad Request"`, `500 → "Internal Server Error"`); ~15 LoC at one site. Or change `Response.reason` to a non-Optional `String` and require the renderer to always populate it. Defer; same disposition class as `Cluster.upstream_protocol`'s defense-in-depth posture (M3 from 05.3 REVIEW).

**M2. The `find_crlf_crlf` byte search at `handler.rs:229-232` is O(n) per call and is called inside the read loop.** The `read_request` loop calls `find_crlf_crlf(&buf)` after every `stream.read`, scanning the entire `buf` from the start each time. For a typical short admin request (< 200 bytes; one read suffices) this is trivially fine. For a request approaching `MAX_REQUEST_HEAD = 8 KiB` it's O(n²) total work. The 8KiB cap bounds the worst case at ~64M byte comparisons, which is sub-millisecond, so the cost is negligible in practice. **Fix sketch:** track a `searched_up_to: usize` cursor and start the next search at `max(0, searched_up_to - 3)` (the 3-byte overlap covers a CRLF spanning two reads). Defer; not a real-world hot path.

**M3. `AdminConfig::from_envoy_config` parses the address as a literal `SocketAddr` only.** `crates/envoy-admin/src/config.rs:21-35` builds `format!("{}:{}", sock.address, sock.port_value).parse::<SocketAddr>()` — a hostname like `localhost` or `0.0.0.0.0` (typo) fails with `BadAddress` and that's the right behavior, but the project's data-plane listeners do the same parse at `crates/envoy-bin/src/main.rs:137-143` and similarly require literal IPs. This is consistent with existing precedent (phase-04 + phase-05 listener bind sites); not a 06.1 regression. Worth noting for stranger-readability — Envoy itself accepts hostnames in `socket_address.address` and resolves them. **Fix:** none required in 06.1; harmonize with whichever phase first ships hostname-resolving listener bind (likely an xDS-family phase). Document in the carryforward inventory.

**M4. The admin listener's accept loop uses a 5-second `DRAIN_BUDGET` constant duplicated from `Listener::serve`.** `handler.rs:22` defines `DRAIN_BUDGET: std::time::Duration = std::time::Duration::from_secs(5)` and `crates/envoy-listener/src/lib.rs:135` defines the identical const inline. Two sources of truth for the same drain budget. Today the values agree; future drift would be silent. **Fix sketch:** either hoist to `envoy-listener` and re-export, or add a `// keep in lockstep with envoy-listener::Listener::serve::DRAIN_BUDGET` comment at one or both sites. Defer; the phase-08 graceful-drain phase is the natural site to consolidate drain semantics.

**M5. The in-process backstop test (`crates/envoy-bin/tests/admin_ready.rs`) inherits the SIGKILL-on-Drop posture from prior phases.** Line 73-75: `let _ = child.kill(); let _ = child.wait();`. Phase-02.2 REVIEW M1's standing carryforward (the `*EchoBackend::Drop` polling-loop blocks on `std::thread::sleep`) is preserved here in shape. The backstop test does not parallelize with other harness tests in a way that would re-expose the carryforward; documenting for completeness. No fix; tracked under the existing chain.

**M6. The empty `tests/fixtures/0011-admin-stats-prometheus/inputs/payload.bin` (0 bytes) is harness-shape consistency only.** The harness drives the request flow synthetically via `Driver::AdminScrape`'s `pre_requests` field; the file is unused. This matches fixture 0010's shape (also 0 bytes empty payload.bin) — consistent with established precedent. Worth noting for stranger-readability: a stranger reading the fixture directory might assume `payload.bin` is meaningful. **Fix sketch:** drop `payload.bin` from `Driver::AdminScrape` fixtures (the file's presence is documented as harness-shape consistency in the README, but the harness does not actually read it). Defer indefinitely; not a defect, just a consistency-vs-clarity tradeoff.
