### Phase-29 carry-forwards (from the phase-28 `REVIEW.md` M28-1..M28-3 - weigh at the phase-29 state-1 brainstorm / planning)

> All 3 are NON-BLOCKING Minors (REVIEW.md APPROVED 0C/0I); none an Envoy-equivalence divergence (the differential gate is green). All three attach to the RING_HASH LB code, so they are naturally weighed when the next LB-family phase (maglev / least_request / subset / locality / priority) or a RING_HASH+EDS-reload phase re-enters that code.

- **M28-1** `maximum_ring_size` is parse-validated + stored but never consulted in the ring build (`crates/envoy-cluster/src/ring_hash.rs`) — only `minimum_ring_size` governs the replica count (`min_ring_size / num_hosts`). Upstream Envoy's ketama build can scale replicas UP toward `maximum_ring_size` for small host counts; envoy-rust's build is `minimum_ring_size`-governed. This does NOT affect the validated 2-host/1024 oracle (512 replicas/host, far under 8M) — which is why 36/36 holds — but a future fixture with a host count where `min/num_hosts` collides with Envoy's max-scaling could silently diverge. **Fix:** no code change for phase-28's validated scope — add one sentence to the `ring_hash.rs` module doc + BEHAVIOR_CONTRACT making explicit that `maximum_ring_size` is parse-validation-only and the build is `minimum_ring_size`-governed. Land opportunistically when the ring code is next touched. _(Reviewer recommendation: a future fixture with an odd host count [e.g. 3 hosts, non-divisible `minimum_ring_size`] would empirically bound this divergence against live Envoy.)_
- **M28-2** the hash-key-absent fallback is the round-robin CURSOR path (`crates/envoy-cluster/src/cluster.rs` `pick` with `None` key), where Envoy's documented fallback is a RANDOM host — a real behavioral divergence. It is acceptable + correctly handled in phase 28: BEHAVIOR_CONTRACT records it as non-deterministic-in-Envoy / NOT differentially asserted, and no fixture exercises it. The backstop's `None → host0 then host1` rotation is a characterization of envoy-rust's internal behavior, NOT an Envoy-matched fidelity contract. Note for whenever a hash-policy-absent path is ever differentially scoped.
- **M28-3** the defense-in-depth `host_index < total` guard in the ring dispatch (`crates/envoy-cluster/src/cluster.rs` ring arm) is dead under the current invariant — the ring is built once from the bootstrap set and never rebuilt on reload (RING_HASH+EDS is out of scope), so `host_index` always indexes `eps` validly. The guard is correct, harmless, and commented; it silently falls through to the cursor path rather than erroring if it ever tripped. Honor it (convert the `ring.is_some()` dispatch to an explicit `lb_policy` discriminant + rebuild the ring on endpoint-set swaps) when MAGLEV or RING_HASH+EDS-reload lands — both already flagged in-code by the Maglev-footgun guard comment.

### Phase-29 state-1 brainstorm (pick + scope; the Maglev / maximal-reuse rationale)

> Authored at the phase-29 state-1 brainstorm (`superpowers:brainstorming`). Records WHY phase 29 is `MAGLEV` + the alternatives weighed; the full reasoning is **ADR-0071**. (Relocates to `STATE_HISTORY.md` per ADR-0035 / §4.1 inv. 9 at the phase-29 state-6 close-out, when row `29` flips `done`.)

- **The pick continues the Load-balancing family with `MAGLEV`** — the SECOND (and last) deterministic, byte-exact-differentiable LB policy after phase-28 `RING_HASH`, explicitly named in the phase-28 SPEC §2.2 as "the LB family's next LB-opener candidate." Among the LB family only the consistent-hashing policies are deterministic (a request hash key → a fixed host); `random`/`least_request` (P2C-random) are non-deterministic → not byte-exact-differentiable without a contract-relaxation ADR (deferred).
- **Maglev is the maximal-reuse next step.** Its REQUEST side is IDENTICAL to RING_HASH (the same route `hash_policy` header → xxHash64 → `Option<u64>` key threaded through `pick()`), so the entire phase-28 request-hash plumbing + the `LbPolicy`/`MaglevLbConfig` config pattern + xxHash64-from-scratch + the two-distinguishable-backend fixture harness (fixture 0036 + `discover_host_lan_ip`/`{{BACKEND_IP}}`) are reused; only the TABLE-BUILD differs (Google's prime-sized permutation table replaces the ketama ring). And like RING_HASH the differential is a NORMAL request/response → LOCALLY observable (no reload trigger), no Linux-CI-only tax.
- **It is the natural M28-3 consumer.** Phase 28 used `ring.is_some()` as the "is RING_HASH" discriminator with a Maglev-footgun guard comment warning a SECOND consistent-hash policy must make the discriminator explicit. MAGLEV is that policy → this phase replaces `ring.is_some()` with an explicit hash-LB dispatch (a load-bearing in-scope refactor; both the round-robin AND the RING_HASH fixture-0036 paths stay behavior-identical).
- **Rejected (ADR-0071):** `least_request`/`random` (non-deterministic); CDS/LDS hot-reload (the deferred xDS layers — heavy swappable-ClusterManager + per-cluster lifecycle churn, split-prone, and CI-only differential; deferred again, not abandoned — the phase-26/27 watcher+swap primitive waits); subset/locality/priority LB (later, layered on the policy-dispatch); the gRPC/ADS transport (still ADR-0014/H2-trailers-blocked).
