- **Pivotal feasibility fact (verified at the brainstorm by reading `pipeline.rs` + `rbac.rs`):** the decode pipeline iterates `self.filters.iter_mut()` passing ONE `&mut FilterRequest` to every filter in chain order (`crates/envoy-filter/src/pipeline.rs:77`), so a filter placed AFTER `header_to_metadata` reads the `req.dynamic_metadata` it wrote in the same pass. The fixture chain order `[header_to_metadata, rbac, router]` (producer before consumer) is REQUIRED. `eval_permission`/`eval_principal(p, &FilterRequest)` already receive the metadata-carrying request.
- **Implementation surface (projected):** config — a `Metadata(MetadataMatcher)` variant on the `Permission` + `Principal` enums (the hand-rolled "exactly one map key" `Deserialize` visitors, `crates/envoy-config/src/bootstrap.rs`) + a `MetadataMatcher`/`MetadataPathSegment`/`ValueMatcher` struct trio (single-segment path, `string_match`-only, reusing the 04.x `StringMatcher`, `deny_unknown_fields`); runtime — `RuntimePermission::Metadata`/`RuntimePrincipal::Metadata` + eval arms reading `req.dynamic_metadata.get(filter)?.get(path[0].key)` + the existing `lower_*` arms (`crates/envoy-filter/src/rbac.rs`); the RBAC decision matrix + `403`+`RBAC: access denied` local reply UNCHANGED.
