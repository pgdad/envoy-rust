- **V-3 — the load-bearing implementation risk: the unread-data RST hazard.** On Linux, closing a socket with unread bytes in its receive queue sends an RST, which can destroy a payload the peer has not yet read. Upstream Envoy closes with `FlushWrite` and the state-0 `client-sends-first` probe saw a clean EOF with a complete payload; envoy-rust's naive `write_all(payload).await; shutdown().await; drop(stream)` may RST where Envoy does not. **Settle this EMPIRICALLY — do not assume the naive path works** — and pin the outcome with a test that writes client bytes BEFORE reading. If it forces a behavior-contract amendment, **ADR-0124** fires.

### Phase-66 state-0/1 brainstorm (active phase)

- **The pick.** Phase 66 opens the **Network filters family**, which had ZERO ROADMAP rows despite being a `BOOTSTRAP_PROMPT.md` §9 family heading since phase 00. Its first member is `envoy.filters.network.direct_response`. The phase also closes a live-witnessed config-validation parity gap (network-filter terminal validation) and adds the differential harness's first read-to-EOF raw-TCP driver.
- **Why this, not a heavier pivot.** xDS CDS hot-reload was the strongest alternative and was REJECTED for a single phase: the phase-26/27 watcher core (`crates/envoy-cluster/src/xds_watch.rs`, `XdsFileWatcher`) IS generic and reusable, but `ClusterManager { clusters: HashMap<String, Arc<Cluster>> }` (`crates/envoy-cluster/src/cluster.rs:908-910`) is a plain immutable map — NOT behind `ArcSwap`/`RwLock` — shared as `Arc<ClusterManager>` to the pool managers, health-check scheduler, and outlier manager. Unlike EDS (which swaps a `RwLock<Arc<Vec<SocketAddr>>>` INSIDE an existing cluster, `cluster.rs:131`), CDS has no map-level swap primitive; the real cost is cluster-lifecycle churn (pool spawn/teardown, health-check probe-task lifecycle, outlier-sweeper lifecycle, in-flight-request safety on a removed cluster) at ~800-1200 LoC with a near-certain §6.1 split. **It loses nothing by waiting** and remains a strong pick for a later multi-sub-phase arc.
- **Why not the cheap leaves.** M64-2 / M57-1 / M53-2 / M64-3 are cosmetic or doc-only and light up **no differential surface**. Phases 53/54/64/65 each added a real cross-proxy witness; a phase whose entire content is doc polish breaks that pattern. None of them touches this phase's surface, so folding them in would be scope creep — they stay LIVE.
- **The empirical target was proven BEFORE the spec was written** (D-3.3: the contract is what Envoy does, not what we remember). Live-Envoy probes against the pinned image established that `direct_response` writes its payload immediately on connect, is byte-identical across connections, ignores client input entirely, is insensitive to client read timing, and closes with a **clean EOF, no RST**. Separately, `--mode validate` established that `direct_response`, `echo`, `tcp_proxy`, AND `http_connection_manager` are ALL terminal upstream. Full evidence: `SPEC.md` §0, R-0.1 … R-0.11.
- **The one real risk is V-3, the unread-data RST hazard.** On Linux, closing a socket with unread bytes in its receive queue sends an RST that can destroy a payload the peer has not yet read. Envoy closes with `FlushWrite` and survives the client-sends-first probe; envoy-rust's naive `write_all` → `shutdown` → `drop` may NOT. **The state-2 PLAN must settle this empirically and pin it with a test that writes client bytes before reading. Do not assume the naive path works.**
- **Do NOT "fix" the `echo` `typed_config` asymmetry.** Upstream Envoy REQUIRES `typed_config` on `envoy.filters.network.echo`; envoy-rust forbids it (`UnexpectedTypedConfig`). Fixture `0001`'s two sides differ accordingly — that is the pre-existing ADR-0014 YAML shim, not a bug. `direct_response` introduces no such asymmetry: both sides of fixture `0071` are identical.
- **`crates/envoy-config/src/error.rs` does not exist.** Locate the real `ConfigError` definition site before planning the new `NetworkFilterNotTerminal` variant (PLAN-VERIFY V-2).
