It was **structurally undiscoverable at phase 66**, which had no non-terminal filter to violate it with. **R-0.2 — the target is deterministic.** On DENY, Envoy writes **zero bytes** and closes with a **clean EOF, no RST**, discarding the client's already-sent bytes; on ALLOW the payload round-trips through the terminal `echo`. The decision is taken **once per connection at establishment, before any downstream byte is read** — which is why the iteration protocol needs only an `on_new_connection` hook and **not** `on_data` (deferred as **CF-67-3**, per §6.3's no-incomplete-stubs rule). **R-0.3/R-0.13 — stats and the INERT case.** Counters are `<stat_prefix>.rbac.{allowed,denied,shadow_allowed,shadow_denied}`; `stat_prefix` is REQUIRED (proto constraint), `rules` is OPTIONAL. **With `rules` omitted the filter is INERT: the connection is allowed and NEITHER counter increments** — it is *not* `default action ALLOW, counted`. A naive default-`Rules` implementation would produce a **stat divergence with no body divergence**. Error precedence was also probed: a chain violating both rules at once reports the **terminal-not-last** error. **These resolve PLAN-VERIFY V-3 and V-6 at state-1.** **R-0.9 — the vacuity trap, and why the harness must grow.** `expected_stats` exists on only three `Driver` variants, all HTTP; the four raw-TCP/TLS variants have none. Because `assert_body_rule`'s `ByteExact` is a bare inequality check, a DENY fixture asserting only *both returned zero bytes* would **pass vacuously even if envoy-rust never implemented RBAC**. Extending the raw-TCP driver family with `expected_stats` is therefore an **in-scope hard requirement**, not polish. ### Phase-67 state-0/1 brainstorm (active phase)

- **`rbac` must NOT be added to `is_terminal_network_filter`** (`crates/envoy-config/src/bootstrap.rs:825`). Its **absence** is what makes it non-terminal — and that predicate's own doc comment names `rbac` as the intended drop-in. Phase 66 wrote it as a per-name predicate rather than a `len <= 1` check precisely so this phase would not have to re-litigate the rule.
- **The bilateral chain-termination rule is NEW and was undiscoverable at phase 66.** Upstream rejects `[rbac]` alone: `non-terminal filter named envoy.filters.network.rbac ... is the last filter in a network filter chain.` Phase 66 enforced only *a terminal filter must be last*; upstream ALSO enforces *a chain must END in a terminal filter*. Phase 66 had no non-terminal filter, so nothing could violate it. Error precedence, probed: a chain breaking **both** rules reports the **terminal-not-last** error.
- **The protocol needs `on_new_connection` ONLY.** Network RBAC decides once per connection, before any downstream byte is read (SPEC R-0.2). Adding an `on_data` hook with no filter to exercise it is the §6.3 anti-pattern; it is deferred as **CF-67-3** to the first payload-parsing network filter (`mongo_proxy`/`zookeeper_proxy`/`kafka_broker`).
- **`rules` omitted ⇒ the filter is INERT.** The connection is allowed and **neither `allowed` nor `denied` increments** (SPEC R-0.13, measured). Do **not** materialise a default `Rules { action: ALLOW, policies: {} }` and tick `allowed` — that is a **stat divergence with no body divergence**, invisible to a body-only fixture.
- **The DENY fixture is vacuity-prone.** `assert_body_rule`'s `ByteExact` is a bare inequality check, so *both proxies returned zero bytes* passes **even if envoy-rust never implemented RBAC**. The `<stat_prefix>.rbac.denied == 1` assertion is what makes fixture `0072` a witness — and **no raw-TCP `Driver` variant carries `expected_stats` today** (only three HTTP ones do). Extending the raw-TCP driver family is an **in-scope hard requirement**, not polish.
- **Fixtures use `any: true` ONLY.** `direct_remote_ip` sees the Docker bridge address (`192.168.65.2` on this host — a documented fragility) and `destination_port` sees a `{{PORT}}` that **differs between the two proxies**. Every IP/port matcher is covered **in-process**, bound to `127.0.0.1`.
- **NAMING HAZARD, the `direct_response` lesson repeating.** `crates/envoy-filter/src/rbac.rs` (1270 lines) is **`envoy.filters.http.rbac`** — a different feature sharing the name. `crates/envoy-filter/` models HTTP filters only and has no network-filter abstraction. `BEHAVIOR_CONTRACT.md` must gain a do-not-conflate banner for `rbac` mirroring the `direct_response` one.
- **V-1 is the biggest unknown:** `Principal`/`Permission` are **shared** with the HTTP RBAC filter; adding L4-only arms may break it if it matches exhaustively. **V-2 is the biggest architectural risk:** `echo::serve` and `direct_response::serve` each own an accept loop while `tcp_proxy`/HCM use `ConnectionHandler`. SPEC recommends **hoisting the accept loop out once** — which also turns **M66-3** into a single fix rather than two, preserving the "echo is the structural model" invariant.
- **M66-5 is CLOSED by recon, not by code.** The empty-`filters: []` chain is **accepted by upstream Envoy** (parity — the phase-66 reviewer's intuition that Envoy rejects it was **wrong**), and `response: {}` is rejected by both. This is why the phase-66 review recorded envoy-rust's behavior and **declined to assert Envoy's**: D-3.3 means the contract is what Envoy *does*, measured.
- **The §6.1 split is projected to FIRE** (~1740 LoC). The PLAN-write owns the decision and must re-derive the estimate. **ADR-0129 is RESERVED** for it.
